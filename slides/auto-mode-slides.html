DEEP DIVE
A separate classifier judges every tool call
Before any gated action runs, Claude Code makes a second API call whose only job is to answer one question: should this be blocked?
Think of it as a safety reviewer sitting next to the agent, glancing at every action before it happens.

THE MODEL
A server-chosen Claude, leaning on prompt cache
The classifier runs on a model Anthropic picks server-side, decoupled from your active /model. In practice, observed as an Opus-class model.
Why it stays cheap: the classifier makes heavy use of prompt caching. The security prompt and the prior transcript are reused across every call, so each new check only pays for the latest turn.

model selection independent of your /model choice switching models doesn't disable the classifier observed on the wire: claude-opus-4-7 prompt cache strategy cache the security-monitor prompt once cache the transcript prefix on every call 1-hour TTL, explicitly opted in ~99% cache hit ratio in steady state

CONTEXT
It sees a filtered version of the whole transcript
The classifier needs to know what you actually asked for, but not everything in the conversation is safe to show it.
Anti-injection by design: tool results are stripped so hostile content in a file or web page can't manipulate the classifier. A separate server-side probe scans incoming tool results before Claude reads them.

THE RULES
What it blocks · what it allows
The classifier trusts your working directory and your repo's configured remotes. Everything else is treated as external.

Blocked by default

• Downloading + executing code (curl | bash)
• Sending sensitive data to external endpoints
• Production deploys and migrations
• Mass deletion on cloud storage
• Granting IAM or repo permissions
• Modifying shared infrastructure
• Irreversibly destroying pre-session files
• Force-push, or pushing directly to main

EXTERNAL / DESTRUCTIVE

Allowed by default

• Local file ops in your working directory
• Installing dependencies declared in lock files
• Reading .env and sending creds to their matching API
• Read-only HTTP requests
• Pushing to the branch you started on, or one Claude created
• Sandbox network requests still route through the classifier

USER INTENT
Boundaries you state in chat are honored
Tell Claude "don't push" or "wait until I review before deploying", and the classifier blocks matching actions, even ones the default rules would allow.
Caveat: boundaries aren't stored as rules. The classifier re-reads them from the transcript on every check, so context compaction can erase them. For a hard guarantee, use a deny rule instead.

ON ENTRY
Broad allow rules get dropped
When you flip into auto mode, Claude Code strips wildcard allow rules that would defeat the classifier. Narrow rules carry over. Everything is restored when you leave.

PROMPT CACHING
Why it's basically free
The transcript only grows by one turn at a time, and the system prompt stays the same. Both get cached server-side.
Result: ~99% of every classifier call is a cache read. Each safety check costs about a fraction of a cent.

FALLBACK
Three strikes,
or twenty total
If Claude keeps hitting blocks, auto mode pauses and Claude Code resumes prompting you for permission.
The thresholds: 3 consecutive blocks or 20 total in a session triggers fallback. An allowed action resets the consecutive counter. Headless -p sessions abort instead.
