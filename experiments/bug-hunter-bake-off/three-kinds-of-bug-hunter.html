Three kinds of bug hunter

The ten strategies in the bake-off look like ten different ideas. They are really three, and they separate on a single question that has nothing to do with what kind of bug each one claims to hunt: where does its list of things to check come from?

10 strategies + 1 written afterwards 1 codebase, ~85 agents 2026-07-30 the scoreboard → why the winners won →
The short answer

A bug hunt is only as good as its list. The best lists are already sitting in the code — every route, every adapter, every writer to one table — because you can read them off with grep, they are never empty, and finishing one is a claim someone else can check.

The two losing families both fail on the list, in opposite directions. One invents its list, so the list has no end and no defensible denominator. The other's list is contingent on the repo having some artifact — a test suite, a git history, a spec — and when the artifact is missing the list is empty and the hunt scores zero without ever starting.

01The question that sorts them

Not "what kind of bug do you look for". That is what each skill's own instructions talk about, and it turned out to be nearly uninformative. This one question predicts both the ranking and, more usefully, whether a strategy will transfer to a different codebase.

Figure 1 — one question, three families
Read the bottom row first. The length of a strategy's list is the property that matters, because a hunt cannot outperform its list. A list that can be empty is a strategy that can score zero for reasons that have nothing to do with how good it is — which is exactly what happened to four of the ten.

03Your codebase switched four of them off

This is the part that makes the scoreboard misleading if you read it as a ranking of strategies. Four entrants were graded on a codebase that could not feed them. Toggle what a repo has and watch the board go dark.

Presets
The left column never changes. Whatever you toggle, the four "list is in the code" strategies stay live, because every repository with more than one of anything has routes, inputs and sibling families. The right column is where the toggles bite. concurrency-hunter is the honest exception on the left — its method reads its list off the code, but it needs the code to have shared mutable state at all, so it dims too. On the arena preset it stayed live, and placed 3rd.

So four of the bottom five are not bad skills. They are skills that were handed a blank page. hyperwhisper-public has a 7.7% test-to-source ratio, so mutation-survivor had almost nothing to mutate. Its 67 commits all landed on a single day, so git-signal had no history to mine. There is no written spec. And the repo is genuinely well factored, so divergence-hunter could not find two implementations of one calculation to disagree with each other. Deleting them on the strength of this run would be reading a precondition failure as a quality failure.

05Why "the list is in the code" is the whole trick

The strongest version of this idea is the one nobody submitted. It is worth walking through because it shows what the property buys you.

Take the eleven speech-to-text provider adapters. They are not copies of each other — each talks to a different API — so nothing that hunts duplicated logic will look at them twice. But they all do the same kind of job, so they should all agree about the rules they follow.

Line them up against one decision point and you get this, which needs no spec, no test suite, no git history and no opinion from you:

The code already decided that outbound calls carry a timeout. It just failed to apply the decision to one of them. You are not arguing about what the code should do, which is the move that generates confident false positives on unfamiliar code. You are pointing out that the project answered the question in writing, next to the version that got it right — and the comment beside the correct sibling is usually sitting there naming the exact harm.

Every convergent finding in the whole run came from this shape, and four separate hunters walked into it accidentally under four different names. None of them had it as a thesis. That is what odd-one-out-hunter now does on purpose.

07Where this could be wrong

  • One codebase, one run. Every number here comes from a single sweep of a single repo. The taxonomy is an argument about mechanism; the ranking attached to it is one data point.
  • The families are my carving, not a measured clustering. Nobody labelled these strategies by list-origin in advance. I sorted them after seeing the results, which is exactly the procedure that produces categories that fit the data too well. The test that would matter is whether the ordering holds on a repo nobody has looked at yet.
  • "Invented list" is a spectrum, not a bin. invariant-hunter authored its list of eight invariants and then swept each one rigorously, which is why it placed 4th rather than at the bottom. subsystem-auditor authored regions and read them, and finished with a 7% proof rate. Same family, very different discipline.
  • Ranks lean on confirmed-finding count, which correlates with compute at r=+0.82 while executable repros do not correlate with it at all. Two entrants also had scoring problems of my own making, documented on the scoreboard.
  • Nothing here measures the bugs that were missed. Every family shares one blind spot the run cannot see: a rule that is uniformly absent across an entire family looks perfectly consistent, and no amount of list-sweeping will flag it.
