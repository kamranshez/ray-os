⏺ I traced it all the way through. Here's what "Conway" is and the honest answer
  on unlocking it.

  What Conway is

  conway is the internal codename for a persistent, containerized agentic Claude
  workspace — shipped inside the claude.ai web bundle that Claude Desktop loads
  (Contents/Resources/ion-dist/), not the desktop Electron code itself (the
  desktop index.js has zero conway references; the only literal in the desktop
  layer is the build dependency @anthropic-ai/conway-client@0.2.0-dev.20260422).

  From the bundle, a Conway is a sandboxed container that has:
  - Its own shell (conway.claudeusercontent.com, "Conway shell handshake")
  - Plugins & skills (drag-drop: "Drop a Conway plugin or skill"), custom tools,
  UI tabs, and context handlers
  - Connectors and webhooks — "Public URLs that wake Conway when external 
  services call them" (/sandbox/conway/webhooks)
  - Schedules — recurring triggers that survive container restarts
  - A per-instance model picker (Opus/Sonnet), MCP refresh
  (/sandbox/conway/refresh_mcp)
  - Routes /conway and /conway/popout, telemetry namespace claudeai.conway.*
  (session_started, shell_handshake_failed, plugin_installed, webhook_created,
  container_restarted…)

  It's explicitly an experiment: badge:"lab", isLab:true.

  How it's gated

  Two server-side feature gates control it, read by the gate function He(...)
  from the account bootstrap gates payload:

  C = He("squares_enabled"); ... C && e.add("conway")          // feature set
  { id:"conway", href:"/conway", label:"Conway", badge:"lab", gate:"conway",
  modes:["chat","cowork"] }

  Plus a Labs verification / attestation flow (labs-verification/attestation
  route). The gates come purely from the server — I checked for any client
  override path and there's none: no _statsigOverride URL param, no localStorage
  override key, no labs opt-in setting you can flip.

  Can you unlock it? Realistically, no.

  - No user toggle exists. The in-app instructions you'd see ("Settings →
  Options → Connect to Conway", "Developer → Conway") only appear after the gate
  is already on — they're not the unlock.
  - You can force the UI but not the feature. If you override He so
  squares_enabled/conway return true (React devtools, a userscript, or patching
  the ce557ac72-*.js / index-BQutSDqp.js bundle in the asar), the "Conway" nav
  item and /conway route will render. But that's exactly the state in your
  screenshot — stuck on "Connecting…" with a placeholder some-container-id. The
  UI needs a real backend: a provisioned container + the
  conway.claudeusercontent.com shell service, which is only granted to
  allow-listed/internal accounts server-side. (Your screenshot is watermarked
  @testingcatalog — that's someone who got the UI painted without a working
  backend, same dead end.)

  Bottom line: Conway is a server-gated lab feature with a hard backend
  dependency. Flipping the client gate is cosmetic — it shows the panel but
  it'll never connect. Actually getting it working requires Anthropic to (a)
  enable the squares_enabled/conway gate on your account and (b) provision the
  container backend. There's no client-side path to a functioning Conway.

❯ whats the server gate                                                         

⏺ The gate that actually switches Conway on is:

  squares_enabled — this is the master gate. In the nav builder:

  C = He("squares_enabled");   // He() = the gate reader, reads the account's 
  server `gates` payload
  ...
  C && e.add("conway")         // Conway only added to the feature set when 
  squares_enabled is true

  It's also what the sidebar uses directly:

  const n = He("squares_enabled");
  n && e.push({ id:"conway", href:"/conway", label:"Conway", isLab:true, ... })

  There's a second, finer gate literally named conway, used on the per-mode nav
  descriptor:

  { id:"conway", href:rI, icon:"Box", label:"Conway", badge:"lab",
  gate:"conway", modes:["chat","cowork"] }

  So the chain is: squares_enabled turns the Conway feature on (sidebar +
  route), and the conway gate is checked on the chat/cowork nav entry. Both are
  evaluated server-side and delivered in the account bootstrap gates: object —
  He(name) just looks them up, there's no local override.

  Related gates that show up alongside it (same lab cluster, in case you want
  the full picture): omelette, cobalt_plinth, epitaxy_tasks_enabled,
  epitaxy_pull_requests_enabled, and the Cowork-backend gates
  yukon_silver_dramatic_shrimp*. But for Conway specifically, squares_enabled is
  the one to look at — it's the top of the chain.
