## Local vs Remote AI Plan Generation — Complete Analysis

Comparative analysis of 13 implementation plans generated by local (Claude Code CLI) vs remote (claude.ai) for the same tasks, across short and long prompts, with and without search.

### What "local" and "remote" mean

When you use an AI coding assistant, there are two fundamentally different ways to ask it to plan work:

**Local** means Claude Code running in your terminal (the CLI tool). It has direct access to your codebase — it can read files, search code, and see your project structure in real time. Think of it as a colleague sitting at your desk, looking at your screen. It plans based on what it can actually see.

**Remote** means claude.ai in the browser. You paste in context — files, specs, descriptions — and it plans based on what you gave it. Think of it as a consultant you briefed over email. It can't browse your codebase, so it has to be more explicit about assumptions, more thorough about what might go wrong, because it can't just "check real quick."

This distinction matters because it changes how each planner behaves. Local can be concise because it trusts it can verify things later. Remote has to front-load all its thinking because it gets one shot.

**Short vs long prompt** is the other axis. A short prompt is a sentence or two describing the task. A long prompt includes context — what exists today, what the constraints are, what's been tried before. The difference is like telling a contractor "remodel the kitchen" vs giving them the floor plan, photos, and your budget.

**Search** means the AI had access to web search during planning. We tested this to see whether real-time information (like reading Gemma 4's actual documentation) changed the plan. Spoiler: it barely did.

### Projects Analyzed

- **AgentStack Plan 31** — LiveKit voice agent (2 plans: local + remote)
- **AgentStack Plan 30** — Service layer extraction (2 plans: local + remote)
- **VidTempla tRPC v10→v11** — Migration (2 plans: local + remote)
- **HyperWhisper Qwen→Gemma** — Model swap (6 plans + 1 prompt, varying prompt length × environment × search)

## Pattern 1: Remote Audits Blast Radius, Local Trusts the Compiler

Remote plans systematically trace every consumer of a changed interface. Local plans make the change and assume the build will catch misses.

**In plain terms:** Imagine you're replacing a light switch in your house. The "local" approach is: swap the switch, flip the breaker back on, see if the lights work. The "remote" approach is: before touching anything, trace which wires go where, check if any other outlets share the circuit, verify the new switch is rated for the load, *then* swap it. Both get the lights working, but if there's a hidden connection to the garage door opener, remote finds it first.

### Exact example: VidTempla tRPC v10→v11

Both plans agree the migration touches only 2 files. But watch what happens next.

**Local plan (entire edge case analysis):**
> "What does NOT change: Server init, API handler, root router, isLoading, onSuccess/onError/onSettled."

That's it — a list of things that don't break, with no evidence.

**Remote plan audits 6 specific locations:**

1. Finds 3 `useQuery(undefined, opts)` call sites — `EditContainerModal.tsx:48`, `EditContainerModal.tsx:53`, `dashboard-sidebar.tsx:199-205` — and confirms the two-arg form still works in v11.
2. Finds all `onSuccess`/`onError` usages are on `useMutation` (kept in RQ v5), not `useQuery` (removed in RQ v5). Names the files: `api-keys.tsx`, `pricing.tsx`.
3. Finds a direct `@tanstack/react-query` import in `members.tsx:31` that bypasses the tRPC wrapper — confirms the import path is unchanged in v5.
4. Flags `@tanstack/react-query-devtools` for upgrade.
5. Catches that `transformer: superjson` needs to appear in **both** `httpLink()` options **and** the top-level `createTRPCNext` config — the local plan only put it in `httpLink()`.

The local plan would probably compile. But if `createTRPCNext` actually requires the top-level transformer (and the remote plan says it does), then local's plan ships a bug that only surfaces at runtime when server-side data isn't deserialized correctly.

### Exact example: AgentStack Plan 30 (Service Layer)

**Local plan scope:** 3 gaps — agents tRPC, actions OAuth, OAuth REST endpoints.

**Remote plan scope:** 5 routers — webhooks, actions, channels, agents, contacts.

Remote finds two edge cases local never encounters because they're outside local's scope:

- **`getExpiredOAuthConnections` returns snake_case.** The frontend expects `provider_account_name`, `expires_at`, `days_until_expiry`. The service returns camelCase. Remote adds an explicit transform in the tRPC procedure. Local doesn't touch this router, so the bug would survive.
- **Contacts `list` uses offset pagination in the dashboard but cursor pagination in the API.** Remote creates a dedicated `listContactsDashboard(orgId, opts)` service function. Local doesn't mention contacts at all.

### Why this matters

Remote's approach costs more tokens but produces plans where a new developer (or AI agent) can implement without needing codebase intuition. Local's approach works for someone who already knows where the landmines are. For agentic coding — where the implementer is another AI agent — remote's blast-radius audit is strictly safer.

**Practically speaking:** If you're the one implementing the plan and you wrote the codebase, local's plan is fine — you already know about `members.tsx` and the devtools package. But if you're handing the plan to a junior dev, a contractor, or an AI agent to execute, remote's plan is the one that won't come back with "it compiled but the dashboard is broken in production." The extra 60 lines of edge case auditing save hours of debugging later.

## Pattern 2: Visible Deliberation Produces Better-Documented Decisions

Remote plans sometimes show their reasoning process inline — weighing options, rejecting alternatives, arriving at a decision. Local plans tend to state the decision directly without showing the alternatives considered.

**In plain terms:** Think of two doctors. One says "take ibuprofen." The other says "you could take ibuprofen, acetaminophen, or aspirin — ibuprofen is best here because you need the anti-inflammatory effect and you don't have stomach issues." Both prescribe the same thing. But if your stomach *does* start hurting, only the second doctor's reasoning helps you understand which alternative to switch to. That's what visible deliberation does — it gives you the map of rejected paths so you can navigate back if the chosen path doesn't work.

### Exact example: HyperWhisper old Qwen directory cleanup

**Local plan (short prompt):**
> "Delete old `qwen/` directory contents on migration since Qwen GGUFs are incompatible with the new Gemma catalog. Log a message so it's traceable."

Decision stated. Rationale compressed into one clause. No alternatives mentioned.

**Remote plan (short prompt, no search) — same decision, visible deliberation:**
> "This ensures users who had Qwen models downloaded don't lose them (though they'll be stale Qwen files — the old models won't appear in the new catalog, so they'll just sit as orphan files. Alternatively, just delete the old directory contents since the models are different anyway. The simplest approach: leave the old directory alone and let users clean it up manually via Finder, or just delete it.)"
> 
> "**Decision:** Delete old `qwen/` directory contents on migration since Qwen GGUFs are incompatible with the new Gemma catalog. Log a message so it's traceable."

Three options weighed — move files, delete files, leave for user. Pros/cons of each. Then a labeled **Decision:** line.

### Exact example: AgentStack Plan 30 `agentSelectColumns`

**Local plan:**
> "Add a `full: boolean` option. When true, use `select()` (all columns) instead of `agentSelectColumns()`."

A parametric solution — clean, but the reader doesn't know why.

**Remote plan — visible deliberation:**
> "The dashboard needs some of these (e.g., `pendingDeleteAt` for the delete warning). Options:
> - Add a `getAgentInternal(orgId, agentId)` to agents-service that returns all columns
> - Or widen `agentSelectColumns` to include `pendingDeleteAt` (it's not secret, just internal)
>
> **Decision:** Add `pendingDeleteAt` and `avatarUrl` to `agentSelectColumns()` in the service (they're needed by dashboard and not sensitive). Keep `identityVerificationSecret` and `svixAppId` excluded."

Two options. Security reasoning for each column. A labeled decision with justification.

### Why this matters

When another developer (or future you) reads the plan six months later, the deliberation trail answers "why not the other way?" without needing to reconstruct the reasoning. Local's decisions are correct but opaque. Remote's decisions are correct and self-documenting. For plans that get shared, reviewed, or handed off — visible deliberation is strictly better.

**Practically speaking:** This has a direct impact on team velocity. When a plan says "delete the old files," someone on the team will inevitably ask "why don't we keep them as a backup?" If the plan already shows that option was considered and rejected (with reasoning), that conversation takes 10 seconds instead of 10 minutes. Multiply that by every decision in a 7-phase plan, and visible deliberation saves entire meetings. It's also why remote plans work better as PRD (product requirements document) substitutes — they carry their own justification.

## Pattern 3: Client Disconnect as Uncovered Failure Mode

This is the most concrete example of remote catching a failure mode that local completely missed.

**In plain terms:** Both plans designed a phone call system where you pay by the minute. Both plans figured out how to start the call and how to charge you when the call ends normally. But only remote asked: "what if the caller just hangs up by slamming the phone down?" Local assumed the phone system would always report back cleanly. Remote didn't trust that — and added a backup way for the caller's phone to say "I'm done" even if the connection dies.

### Exact example: AgentStack Plan 31 (Voice Agent)

The voice call lifecycle depends on a LiveKit webhook (`room_finished`) to trigger credit finalization. Both plans describe this flow.

**Local plan — 4 API routes:**
- `POST /api/voice/start` — create room, generate token, pre-auth credits
- `POST /api/webhooks/livekit` — receive webhook, trigger finalization
- `POST /api/voice/search` — agent tool endpoint for RAG
- `POST /api/voice/escalate` — agent tool endpoint for escalation

**Remote plan — 5 API routes (same 4, plus):**
- `POST /api/voice/end` — "client-initiated graceful end (backup to webhook)"

The remote plan anticipated: what happens if the user closes their browser tab, loses internet, or the WebRTC connection drops before LiveKit sends the webhook? The pre-authed credits are stuck in limbo. The `/end` endpoint lets the client-side code fire a `navigator.sendBeacon()` on `beforeunload` to trigger finalization immediately.

Local's plan would eventually finalize — LiveKit's `emptyTimeout: 60` would close the room after 60 seconds of no participants, triggering the webhook. But for 60 seconds, the user's credit balance shows the full pre-auth deduction instead of the actual usage. For a call that lasted 30 seconds on a provider costing 9 credits/minute, that's the difference between showing -9 credits and -5 credits for a full minute.

### Why this matters

The `/end` endpoint isn't a feature — it's a trust signal. Users who see their credits correctly refunded within seconds trust the billing system. Users who see a phantom deduction for 60 seconds before it corrects itself file support tickets. Remote's plan prevents a support burden that local's plan creates.

**Practically speaking:** This is the kind of thing that separates a product that "works" from one that "feels right." The voice call technically functions without the `/end` endpoint — credits eventually correct themselves after 60 seconds. But during those 60 seconds, every user who checks their balance thinks they were overcharged. That's a support ticket, a trust hit, and maybe a churn event. The fix is ~30 lines of code. Remote caught it during planning; local would have discovered it from a customer complaint. The cost difference between fixing something in a plan vs fixing it after a user reports it is roughly 100x in time and 1000x in trust.

## Pattern 4: Plans Converge as File Count Increases

The gap between local and remote plan quality is inversely proportional to the number of files touched. On few-file tasks, the gap is enormous. On many-file tasks, it nearly disappears.

**In plain terms:** Imagine two people packing for a trip. One is meticulous, one is fast. If you're packing a carry-on (small task), the meticulous packer adds a first-aid kit, a backup charger, and rain gear you didn't think of — the gap is huge. If you're packing a moving truck (big task), both people end up loading the same furniture, the same boxes, the same appliances — because when the job is mostly about *not forgetting items from a long list*, both approaches converge on the same checklist. The meticulous packer's advantage shrinks because there are fewer hidden surprises in "pack every room" than in "pack just the essentials."

### The evidence

**VidTempla tRPC v10→v11 — 2 files changed:**

Local: 40 lines. States what changes. Zero edge cases audited.
Remote: 100 lines. States what changes. 5 edge cases audited, 6 specific call sites verified.

Gap: **massive**. Remote is strictly a superset. Local's plan has a potential runtime bug (missing top-level transformer).

**AgentStack Plan 31 — ~15 new files, ~5 modified:**

Local: 7 phases, full schema, full API spec, dependency graph.
Remote: 7 phases, full schema, full API spec, architecture diagram.

Gap: **moderate**. Remote adds `/end` endpoint, separate booleans, decimal credits. Local adds demo mode. Both are implementable plans that would ship working software.

**HyperWhisper Qwen→Gemma — ~21 Swift files + 40 localization files:**

Local (long): 19 Swift files enumerated with exact line numbers, Core Data v24, 40 localization files with key-level detail.
Remote (long): 21 Swift files enumerated with exact line numbers, no Core Data version, 40 localization files with key-level detail plus runtime error strings.

Gap: **narrow**. Local wins on Core Data versioning. Remote wins on localization completeness. Both enumerate nearly the same files. The plans are ~90% identical in substance.

### Why this happens

When a task touches 2 files, the plan's value is almost entirely in anticipating what *else* might break. This is where remote's blast-radius auditing shines — it searches for consumers, checks call sites, flags edge cases.

When a task touches 60 files, the plan's value shifts to enumeration — listing every file, every change, every localization key. Both environments are equally good at enumeration because it's mechanical. The edge cases that remain (Core Data versioning, runtime error strings) are fewer and more evenly distributed between local and remote.

The practical implication: for small, high-leverage changes (library upgrades, API contract changes, billing logic), always prefer remote or at minimum use it to audit the local plan. For large, mechanical changes (rename across codebase, model swap, localization), either environment works.

**Practically speaking:** This insight saves you money and time. You don't need to run both planners on every task. The rule of thumb is simple: **count the files**. If the change touches fewer than 5 files, invest in a remote plan (or at least use remote to review the local plan) — the ROI is highest there because remote will find hidden connections you missed. If the change touches 50+ files, a local plan is sufficient — you're paying for enumeration, not insight, and both enumerate equally well. The sweet spot for running both is the 5-20 file range, where the gap is moderate and either planner might catch something the other missed.

There's also a deeper reason this happens. Small changes are like surgery — precision matters more than speed, and one wrong cut has outsized consequences. Large changes are like landscaping — you're reshaping the whole yard, and the risk is spread across many small actions rather than concentrated in one. AI planners, like humans, are better at checklists than at anticipating hidden dependencies. So as the task shifts from "anticipate what breaks" to "don't miss any files," the advantage of the more thorough planner fades.

## Pattern 5: Naming Decisions Reveal Planning Horizon

**In plain terms:** When you name a folder on your computer, you're making a bet about the future. Name it "vacation-photos-2026" and it works for one trip. Name it "travel" and it works forever. Both organize the same photos today, but one creates work next year and the other doesn't. The naming decisions across these 13 plans reveal which planner is thinking about this trip vs all future trips.

### Exact example: Qwen→Gemma provider enum

All 6 plans rename the same Swift enum case. Their naming choice reveals how far into the future they're planning:

| Plan Variant | Chose | Raw Value | Implication |
|-------------|-------|-----------|-------------|
| Short Local | `localLLM` | `"local_llm"` | Next model swap is free |
| Short Remote (Search) | `localGemma` | `"local_gemma"` | Next model swap requires another rename |
| Short Remote (No Search) | `localLLM` | `"local_llm"` | Next model swap is free |
| Long Local | `localLLM` | `"local_llm"` | Next model swap is free |
| Long Remote | `localLLM` | `"local_llm"` | Next model swap is free |

Local plans: 3/3 chose generic. Remote plans: 2/3 chose generic, 1/3 chose model-specific.

The short remote plan with search — the only one to choose `localGemma` — was also the only plan that had real-time access to Gemma 4's documentation. Paradoxically, having more information about the *specific model* biased the plan toward model-specific naming. The plans without search, forced to reason from principles rather than product pages, defaulted to the generic name.

### Why this matters

`localGemma` means that when Gemma 5 ships (or Llama 4, or Mistral Next), you need to:
1. Rename the enum case and raw value
2. Migrate Core Data strings again
3. Update 40 localization files again
4. Audit every consumer file again

`localLLM` means you update the model catalog in one file and you're done. The naming decision made in 5 seconds during planning creates or eliminates 3-4 hours of work during the next model swap.

**Practically speaking:** This is one of the rare cases where local plans are *objectively* better, not just stylistically different. The naming choice cascades through the entire codebase — enum cases, Core Data stored strings, 40 localization files, environment objects in SwiftUI. Choosing `localGemma` means the *next* person who does this exact same task (swap one local model for another) has to touch all 60+ files again. Choosing `localLLM` means they change one catalog file. Over the lifetime of a product that ships local AI models, this decision could save dozens of hours. And the interesting meta-insight: the plan that had *the most information* about Gemma (the one with search enabled, reading Gemma's actual docs) was the one that made the worst naming choice — because it was so focused on Gemma specifically that it forgot there would be a Gemma 5.

## Pattern 6: Search Doesn't Change Architectural Decisions

**In plain terms:** We assumed that giving the AI access to Google would make its plans better — like how a student with open notes should outperform one without. Turns out, for planning tasks, the "notes" don't help much. The AI already knew enough from its training. Search confirmed details (like exact download URLs) but didn't change any structural decision. It's like giving a chef a cookbook when they already know the recipe — they might double-check the oven temperature, but they're not going to rethink the dish.

### Exact example: Short Remote (Search) vs Short Remote (No Search)

These two plans were generated from the same short prompt, same remote environment. The only difference: one had web search enabled.

**Structural overlap:** >95% identical. Same phases, same file list, same migration strategy, same verification steps.

**What search added:**
- Slightly more confident HuggingFace download URLs
- The search variant wrote `https://huggingface.co/unsloth/gemma-4-E2B-it-GGUF/resolve/main/gemma-4-E2B-it-Q4_K_M.gguf` — a fully qualified path
- The no-search variant wrote the same URL — suggesting the model's training data already contained Unsloth's URL patterns

**What search didn't change:**
- Model count (4 in both)
- Sampling parameters (identical)
- Naming convention (both chose their convention independently of search)
- Migration strategy (both deliberated, both chose delete)
- File count (both ~21 files)

The model already knew enough about Gemma 4 from training data to generate a correct plan. Search confirmed facts but didn't introduce new architectural ideas.

**Practically speaking:** This has real cost implications. If you're paying per search query or for a search-enabled tier, you can skip it for planning tasks. Search becomes valuable for *implementation* (checking current API docs, verifying if a function signature changed in the latest release) but not for *architecture*. Save your search budget for when you're writing code, not when you're planning it. The one exception: if the technology you're planning around was released *after* the model's training cutoff, search becomes essential. But for anything within the training window, the model already internalized the documentation.

## Gaps in Both (neither environment ever produced these)

These are the things that *no* plan — local or remote, short or long, with or without search — ever mentioned. This is the shared blind spot of AI planning today.

- **Rollback plans** — no plan describes how to revert if production breaks. Every plan assumes forward-only progress. In reality, about 1 in 5 deploys has an issue that requires rolling back. A plan without a rollback section is like a recipe without "if the sauce breaks, here's how to fix it."
- **Feature flags** — everything ships as all-or-nothing. No plan suggests "enable for 10% of users first." For a voice calling feature that touches billing, this is risky. If the credit math is wrong, 100% of users are affected on day one.
- **Performance benchmarks** — no Gemma 4 vs Qwen 3.5 quality/speed comparison. We're replacing the engine, but no plan asks "is the new engine actually better?" Both planners assumed the newer model is better because it's newer.
- **Monitoring/alerting** — no error rate dashboards or anomaly detection. The voice plans specify how credits work but not how you'd detect if credits are being miscalculated at scale.
- **Per-user rate limiting** — voice endpoint has concurrent limits but no per-user throttle. One user could theoretically burn through organization credits by starting calls in rapid succession.
- **Accessibility** — voice UI has no screen reader or reduced motion consideration. A voice calling overlay with animation states (listening/thinking/speaking) needs accessibility thought.

**Why this matters practically:** These aren't nice-to-haves — they're the difference between a feature that ships and a feature that survives its first week in production. The takeaway: after generating any AI plan, add these sections manually. Think of the AI plan as a first draft that covers "what to build" but not "what to do when it breaks."

## Optimal Combination Strategy

The core insight is that you should almost never use just one plan. Each environment has a distinct strength, and merging is cheap compared to discovering a gap during implementation.

**For each project:**

- **AgentStack Plan 31:** Remote's architecture (separate `voiceAgentEnabled`, `decimal(10,4)` credits, `/end` fallback endpoint, explicit error codes) + Local's file organization (dedicated `voice.tsx` settings page instead of cramming into `chat.tsx`)
- **AgentStack Plan 30:** Remote's wider scope (all 5 routers + contacts refactor) + Local's OAuth REST endpoints (net-new API surface). Use Remote's time estimates for scheduling.
- **VidTempla tRPC:** Remote plan verbatim — it's strictly a superset of local, catches the `createTRPCNext` transformer detail, costs nothing extra.
- **HyperWhisper Qwen→Gemma:** Local long prompt as the base (generic naming, Core Data v24, exact line numbers, PR #118 awareness) + Remote long prompt's consumer file table and runtime localization string audit.

**For future plan generation — a simple decision framework:**

| Question | Answer | What to do |
|----------|--------|------------|
| How many files does the change touch? | <5 | Always generate remote (or use remote to audit local). The gap is largest here. |
| | 5-20 | Generate both and merge. This is the sweet spot where both catch things the other misses. |
| | 50+ | Either works. Save the remote budget for a different task. |
| Does the task involve billing or money? | Yes | Use long prompt + remote. Short prompts drop financial precision (integer vs decimal). |
| Does the task involve data migration? | Yes | Use long prompt + local. Only long local prompts produced proper schema versioning. |
| Will someone else implement this plan? | Yes | Use remote. Visible deliberation and blast-radius auditing make the plan self-contained. |
| Are you implementing it yourself, today? | Yes | Use local. It's concise, assumes your codebase knowledge, and won't waste your time explaining things you already know. |

**After any AI plan, manually add these sections (no planner produces them today):**
- Rollback steps — what to do if the deploy fails
- Feature flag strategy — how to gradually expose the change
- Monitoring hooks — what dashboards or alerts to check post-deploy

## Pattern 7: You Might Be Getting a Different Planner Than You Think

There's a hidden variable in all of this that most people don't know about: **the remote planner isn't always the same planner.**

### The three ultraplan prompt variants

When you trigger a plan on claude.ai (the remote "ultraplan" mode), Anthropic's server silently assigns you one of three different planning prompts:

1. **simple_plan** — The lightest version. No subagents, no diagrams. The AI explores the codebase directly, writes a plan, and hands it back. Pipeline: Plan → Edit → Execute. Takes "a few minutes."

2. **visual_plan** — Same as simple_plan, but with an added instruction to include Mermaid or ASCII diagrams when the change has meaningful structure (dependency order, data flow, before/after). The diagram shows the shape; the prose provides the substance.

3. **three_subagents_with_critique** — Fundamentally different. Spawns 3 parallel subagents: one to understand existing architecture, one to find all files needing modification, one to identify risks and edge cases. Then a *fourth* critique agent reviews the synthesized plan for missing steps. Pipeline: Scope → Critique → Edit → Execute. Takes "10-30 minutes."

**You don't choose which one you get.** Anthropic controls this via a server-side config flag (`tengu_ultraplan_prompt_identifier`). It's an A/B test — you type "ultraplan" and get whichever variant the server assigns. There's no user-facing toggle.

### Why this explains some of the inconsistencies

This is likely a factor in the variation I was seeing across remote plans. Some remote plans were noticeably more thorough than others — the ones that felt like they caught every edge case, audited every consumer file, and showed visible deliberation? Those were probably hitting the **three_subagents_with_critique** variant, which literally has a dedicated agent for "identify risks and edge cases" plus a critique pass that checks for missing steps.

The simpler remote plans that behaved more like local — concise, forward-only, no deliberation trail? Those were probably the **simple_plan** variant, which is basically the same approach as local but without direct codebase access.

**In plain terms:** Imagine you go to a restaurant three times and the food quality varies wildly. You might think the chef is inconsistent. But actually, the restaurant has three different chefs and you get randomly assigned one each visit. That's what's happening with remote planning — you're not always getting the same "chef," and the deep planning variant (with the critique agent) produces measurably better results than the simple one.

### What this means practically

- **The "remote is more thorough" finding may be partially an artifact of getting the deep variant.** When I got plans that audited blast radius, showed deliberation, and caught client disconnect failure modes, those were likely the multi-agent variant doing its job.
- **The inconsistency itself is a finding.** You can't rely on remote always being thorough, because you might get the simple variant. This strengthens the case for always generating both local and remote — you're hedging against which remote variant you happen to get.
- **The deep variant was genuinely impressive.** The plans I got from what was likely `three_subagents_with_critique` were the ones that caught the tRPC transformer issue, the credit precision gap, and the client disconnect. Having a dedicated "risk agent" and a "critique agent" is a real architectural advantage — it's like having a peer review built into the planning process.
- **You can't force the deep variant today.** There's no user-facing way to select it. The `promptIdentifier` can be passed via the API, but the UI doesn't expose it. So for now, the best strategy remains: generate multiple plans and merge, because you can't guarantee which variant you'll get.

## One-Sentence Takeaway

Remote plans find more bugs in today's change while local plans prevent more bugs in tomorrow's change — generate both, merge the best of each.
