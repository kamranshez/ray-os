Observer Agents vs Dynamic Workflows

Two different answers to the same fear: the agent will cheat to finish and I won't notice. They work on different axes — a workflow imposes structure, an observer adds supervision — which is why the instinct to compose them is right. The catch found in the binary: today, they don't compose. So it's an either/or commitment, per task.

The load-bearing finding

A dynamic workflow's agent() calls will not attach an observer — even if the target agent definition declares observer: <name>. Observer arming happens in exactly two places: the main session loop and the Task/Agent spawn handler. The workflow path calls the low-level subagent runner r8 directly and never touches the arming functions (V3r / Cqr). Across the entire workflow module, references to those are zero.

They share a runner and an agent registry, but the observer layer sits above the runner, and the workflow path enters below it. You cannot put a watcher on a workflow stage.

01 — The two architectures

Structure vs supervision

A workflow chops one big task into stages and inspects what came out of each before the next begins. An observer leaves the task whole and watches how it is being done, turn by turn. The first buys you checkpoints; the second buys you a witness.

02 — What each one can actually see

The result vs the trajectory

This is the axis that decides everything else. A workflow gate is handed an artifact — the diff, the report, the test output — and judges it. An observer is handed the sequence of moves that produced the artifact. A hollow green test suite passes the gate every time; it does not survive someone watching the commit that deleted the test.

The gate is not stupid — it is structurally blind. The evidence of the cheat was destroyed before the artifact was produced.

The counter-argument worth taking seriously: a well-built workflow can thread stage 1's research into stage 3's verifier, recovering some cross-stage checking. True — but it recovers cross-output consistency, not the trajectory. The turns inside a stage remain invisible to it.

03 — The observer loop, exactly

A witness with one tool and no hands

Mechanism from the binary. Cadence is per turn, not per tool call: events are captured during the turn and flushed when the turn ends. The digest is read-only data wrapped in activity tags, each segment truncated at 2000 characters. The observer's only tool is ObserverReport, which injects a short text report into the worker's own stream. It cannot block, deny, or rewrite anything.

"The expected steady state is silence" — from the observer's own embedded system prompt.

Two consequences that fall straight out of the mechanism:

  • It is advisory. The report lands as text. The worker can read it and carry on regardless. The value is early independent noticing, not enforcement.
  • It is one turn late. The tool call has already run by the time it appears in a digest. For irreversible actions — sending, publishing, spending, dropping a table — the observer is a smoke alarm that goes off after the fire. Those need a real gate, which is exactly what an observer is not.

04 — Why they don't compose

Three spawn paths, two of them armed

The natural move — "put an observer on the one open-ended stage of my workflow" — is not available. Observer arming lives above the shared subagent runner. The workflow's agent() primitive enters below it, so the observer: field on a resolved agent definition is simply never read on that path.

Shared runner, independent observer layer. The built-in workflow-subagent type carries no observer field at all.

Also worth knowing: no chaining. An observer cannot itself declare an observer — the arming code explicitly bails and logs that it is ignoring the declaration.

05 — The routing test

Two questions, asked in order

Because you have to commit to one architecture, the decision needs to be answerable up front. Ask decomposability first, then verifiability. Reach for a workflow by default — it dominates most engineering work — and spend an observer only in the band that resists both.

Workflow-first. The second question is really "does the how matter, or only the what?" — if only the what, a gate covers you. The observer earns its keep in the leftover band, not as a default.

06 — The same test as a 2×2

Where the disagreement actually lives

The "observers are redundant" argument is correct in the top-left quadrant — which happens to be where most planned engineering work sits, and where anyone who plans thoroughly up front spends their time. The argument stops holding as you move down and right.

Observer
Research, brainstorming, judgement calls, docs, long labelling runs, migrations that drift. No clean stages, and "is this good?" isn't checkable after the fact. Watch the method live.

The honest concession: if you always plan thoroughly and decompose before you build, you live in the top-left and an observer will feel redundant. That is not a flaw in the observer — it is the routing test working.

08 — The third thing in the picture

Observers move rare exceptions into their own layer

A separate angle worth keeping: every "NEVER do X" rule you bolt onto a worker's prompt is paid for on every turn, in attention and context, to catch something that fires 1% of the time. Moving those rules to a watcher keeps the worker's prompt focused on the job, and puts the exceptions somewhere they can be reused across workers.

09 — Turning it on

Three conditions, all required:

  • CLAUDE_CODE_EXPERIMENTAL_OBSERVER_AGENTS must be set — required, unset means off.
  • tengu_observer_agents_enabled — defaults to true. It is a server kill-switch, not the on-switch.
  • Background tasks must not be disabled.

So the feature reads as "off by default" in practice even though its flag defaults on — the env var is the real gate. Then add observer: <name> to a worker agent's definition and write the observer as a short prompt naming exactly what to protect.
