1M Context Window — 5 Script Variations

1. The Two Failure Modes

Structure around what goes wrong, not what goes right

Hook

There are two ways to fail with a 1M context window. Most people will hit both.

Failure 1: Treating it as working memory

You load everything in and start coding. At 200K it's great. At 400K it's fine. At 600K the model starts repeating itself. Google's Gemini research found it clearly — past a certain point, the model defaults to "repeating actions from its vast history rather than synthesizing novel plans."

It's not forgetting things. It's the opposite — it remembers too much. Every past decision becomes gravity pulling it toward the same patterns.

The fix: use the big window for reading, not doing. Load the whole codebase, understand the full picture, then distill a plan. Do the work in fresh, smaller sessions where each one starts clean.

Failure 2: Never using it

The opposite mistake. You keep sessions short because you heard long context degrades quality. So you never load the full picture. You work from fragments. You miss the connection between module A and module Z because you never saw them in the same window.

The fix: the reading phase should be long. That's where 1M earns its keep. You just shouldn't also do the execution there.

The sweet spot is being aggressive about intake and disciplined about execution.

The Coordination Problem

Once you're dispatching work to subagents, a third failure mode appears: the coordinator losing track. Each subagent reports back — files changed, decisions made, tests run. After 5-6 reports, that's 20-30K tokens stacking up. Before 1M, this is where compaction would hit and the coordinator would start approving contradictory work.

This is 1M's real unlock for coding. Not longer execution — longer coordination. The coordinator can absorb 15-20 subagent reports without losing the thread. The 15th review is as informed as the 1st.

The Decision Rule

Before your next action, ask: am I reading or doing?

Reading → let the window fill. Doing → keep it lean. Coordinating → this is what 1M was actually built for.

When to Reset

Does the context from your last task help the next one? If yes, keep going. If no, you're carrying dead weight. Feature A's context is noise when you're building feature B — unless they share state. Testing feature A? That context is pure signal. Keep going.

2. The Spectrum

One framework: task intensity determines session strategy

Hook

There's one question that determines how you should use 1M context: how hard is what you're about to do?

Low Intensity: Just Keep Going

Replying to 30 emails. Reviewing a batch of PRs. Renaming things across a codebase. Translating content. Filling out forms via browser automation.

These tasks don't require the model to hold complex decisions in its head. It needs to maintain a simple pattern across many repetitions. 1M context is a straight upgrade — you just don't run out of runway. Before, browser workflows would break at step 15. Now they handle 30-40 steps without losing continuity.

No orchestration needed. No subagents. One session, steady work.

Medium Intensity: Read Then Do

A feature that touches 5-10 files. A bug that requires understanding a subsystem. Anything that fits in roughly 200-300K tokens of actual implementation.

Load the relevant code, understand it, plan the approach, then implement — all in one session. The 1M window means you can load more context upfront without worrying about running out of room for the work itself. You get better plans because you see more of the codebase before you start.

High Intensity: Scout, Dispatch, Verify

A feature that touches 20+ files. A refactor across multiple subsystems. Anything where a single session would hit 400K+ tokens of implementation.

This is where the session splits into three roles:

Scout: Load everything. Understand the full architecture. Produce a detailed plan — which files change, what each change does, what depends on what, what could break.

Workers: Each subagent gets one piece of the plan. Fresh context, focused task. They implement better because they're not carrying 300K tokens of unrelated decisions.

Verifier: The coordinator holds the original plan plus every worker's report. It checks: do the pieces fit? Did anyone contradict the plan? Are there gaps?

1M's real contribution: the verifier can now hold 15-20 worker reports plus the full plan. Before, it would lose the early reports to compaction and approve contradictions it couldn't see.

The Gradient, Not the Binary

This isn't three discrete categories. It's a spectrum. As task complexity increases, gradually shift from "do it all here" toward "read here, do elsewhere." The transition point is roughly when you expect implementation to exceed 200-300K tokens.

Simple → one session, let it run. Medium → read wide, implement here. Complex → read wide, dispatch narrow, verify wide.

3. Reading vs. Writing

The core insight distilled to its simplest form, then expanded

Hook

1M context is a reading upgrade, not a writing upgrade. That one sentence changes how you use it for everything.

The Core Principle

Long context makes the model better at understanding. It does not make the model better at producing. In fact, production quality degrades as context grows — the model starts repeating past patterns instead of generating fresh solutions.

So you want maximum context when absorbing information. And minimum context when generating output.

Read with the full window. Write with a clean one.

Applied to Code

Reading phase: load the entire repo, all the tests, the deployment config, the CI logs. See every connection. Understand the architecture completely. Produce one artifact: a detailed implementation plan.

Writing phase: start fresh sessions. Each one gets the relevant slice of the plan and the files it needs to touch. It writes better code because it's not drowning in 500K tokens of things it already read.

Verification phase: back to reading mode. Load the plan, every implementation report, the changed files. Read it all. Check coherence. This is reading, not writing — so the full window helps rather than hurts.

Applied to Data

Reading: load all 12 files. See cross-file patterns. But here's the nuance — reading is influenced by order. What the model read most recently gets more attention. So read the same files in different orders. Each pass surfaces different connections. Combine the readings.

Applied to Repetitive Tasks

Here the distinction collapses. Replying to emails, renaming variables, filling forms — this is "writing" that's so simple it's basically pattern application. There's no creative degradation because there's no creativity required. The full window just means you can apply the pattern longer.

The Meta-Rule

Before any session, ask: is this session primarily reading or writing?

If reading → fill the window. That's its strength.

If writing → keep it lean. The accumulated context from your last reading session is available as an artifact (the plan), not as raw context.

If you're done with one type and switching to the other → start fresh. Unless the next task directly builds on the current context.

4. The Coordination Tax

Reframed around the problem 1M actually solves

Hook

The hardest problem in AI-assisted coding isn't getting the model to write good code. It's getting 10 pieces of good code to work together. 1M context solves that problem.

Why Single Sessions Break

A single session coding for a long time hits two walls. First, retrieval — MRCR benchmarks show the model's ability to find information in its own context drops from 91.9% to 78.3% at 1M tokens. Second, and worse, creativity — Google's research shows the model starts repeating past actions instead of generating new approaches. It codes like someone who's been awake for 36 hours.

So you split the work. Subagents. Each one starts fresh, codes one piece well.

The Problem That Creates

Now you have a coordination problem. Someone has to hold the plan, receive every report, check for contradictions, catch gaps, verify the assembled result.

Each subagent report is 3-5K tokens. After 6 reports, that's 20-30K on top of the plan, the architecture context, and your messages. Before 1M, this is where the coordinator would hit compaction. The plan gets summarized. Early reports get compressed. The coordinator approves work that contradicts decisions it can no longer see.

The coordination tax: every subagent that reports back costs context. Before 1M, you could afford maybe 5-6 reports. Now you can afford 15-20+.

What This Actually Looks Like

Session loads the codebase. Understands architecture. Writes a detailed plan — files, changes, dependencies, risks.

Dispatches workers. Each gets their slice. They implement in fresh windows. Quality stays high because each one is thinking, not repeating.

Workers report back. The coordinator absorbs each report. Checks it against the plan. Checks it against every previous report. At report 15, it still has report 1 in full fidelity.

Final synthesis. Does the assembled whole match the original intent? This is the step that was impossible before 1M. The coordinator would be at 500K tokens, deep in the degradation zone. Now it's at 200-300K — still sharp.

The deeper insight: by delegating heavy implementation to subagents, the coordinator stays lean. When synthesis happens — the most important step — the model is still at its best.

The Exception

If there's no coordination — one task, repetitive, low complexity — there's no coordination tax. Just let the session run. 1M means you can reply to 30 emails or automate 40 browser steps without the session dying halfway through.

Session Boundaries

The coordination context is cumulative — every report builds on the last. Stay in the session while coordinating. But when the project's done, that coordination history is dead weight. Start fresh.

5. Three Numbers

Built around concrete thresholds that make decisions easy

Hook

You don't need a framework for 1M context. You need three numbers: 200K, 500K, and 1M.

0-200K: The Sharp Zone

The model is at its best. Full retrieval accuracy. Novel reasoning. Creative problem-solving. If your task — reading and implementation combined — fits in 200K, just do it in one session. No orchestration needed.

This covers most everyday coding. A feature that touches 5-10 files. A bug investigation. A refactor within one subsystem.

200K-500K: The Transition Zone

Retrieval is still solid. But creative output starts degrading. The model begins recycling patterns from earlier in the session. It's subtle — the code still works, but it starts looking like copies of what it already wrote.

If you're in this zone and doing complex creative work, consider splitting: read phase here, implementation dispatched to subagents. If you're doing simple repetitive work, keep going — there's no creativity to degrade.

500K+: The Intake Zone

This is where you should be reading, not writing. Loading codebases. Absorbing logs. Understanding architecture. The model can still find information — MRCR only drops to 78.3% at 1M — but its ability to generate novel solutions is significantly reduced.

Use this zone for:

  • Building the complete picture before planning
  • Coordinating subagent reports (reading, not generating)
  • Synthesis — checking assembled work against the original plan
  • Repetitive tasks that don't require novelty
Below 200K: do everything here. 200-500K: transition to dispatch. Above 500K: read and coordinate only.

How the Numbers Work Together

The coordinator loads 300K of codebase context. Plans at 350K. Dispatches workers — each starts at 0, finishes around 50-100K. Workers report back. The coordinator absorbs reports, reaching 400-600K. But it's reading reports, not generating code. Synthesis happens at 500K — still effective for reading and checking coherence.

If the coordinator had done the implementation itself, it would be generating code at 500K+. That's the degradation zone. By offloading implementation, the hard creative work happened at 0-100K in each subagent. The coordinator only does reading and verification in the upper zones — exactly what those zones are good for.

Data Analysis Trick

Load files in different orders across separate sessions. Each session uses 200-400K. But each makes different connections because of recency and positional effects. Three passes with different orderings gives you coverage that one pass at any size can't match.

When to Reset: The One Question

Does the context you're carrying actively help the next task? If yes, continue. If not, you're wasting sharp-zone capacity on noise. Start fresh.
