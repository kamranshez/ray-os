Codex /goal

A persistent, budget-aware autonomous loop. You give Codex a high-level objective once. It keeps working toward it across turns, watches its own token spend, and only stops when it can prove the objective is done.

The 30-second version

codex
$ codex ▌ ready › /goal ship the auth-rewrite branch with full test coverage --token-budget 200000 ✓ goal set (active · budget 200k tokens) [turn 1] reads diff, runs tests, identifies 3 failing cases [turn 2] ↳ auto-continued — fixes case 1, re-runs tests [turn 3] ↳ auto-continued — fixes case 2 and 3 [turn 4] ↳ auto-continued — completion audit: all 3 fixes verified calls update_goal(status="complete") ✓ goal complete — tokens: 47,310 of 200,000 · time: 312s

You typed one command. Codex ran four turns on its own, then declared itself done. No /continue, no nudging, no "are you still there?".

The four states a goal can be in

● active
Working. Idle turns are auto-continued.
● paused
You hit Ctrl-C or ran /goal pause. Resumes on next thread load.
● budgetLimited
Token budget exhausted. Model is steered to wrap up, not start new work.
● complete
Model called update_goal after a passing audit.

Source: codex_protocol::ThreadGoalStatus · transitions are owned by the runtime, not the model — the model can only mark complete.

How a single goal turn actually flows

  1. Turn starts. Runtime reads the active goal from the per-thread state DB and snapshots the current token usage as the baseline.
  2. Model works. Tools run. After every non-goal tool call, the runtime accounts the delta: (non_cached_input + output_tokens) charged against the goal's budget; wall-clock seconds charged against time.
  3. Budget check. If accumulated tokens crossed the budget, the goal flips to budgetLimited and a hidden developer message is injected mid-turn telling the model to wrap up.
  4. Turn ends. Final accounting pass. If no other input is queued and the goal is still active, the runtime spawns its own next turn — no user input required.
  5. Continuation prompt. The auto-spawned turn opens with a developer message containing the objective, current spend, remaining budget, and a strict "completion audit" instruction.
  6. Loop. Repeat from step 1 until the model calls update_goal(status="complete") — or the user pauses, clears, or interrupts.

The three model-facing tools

create_goal

Starts the loop. One goal per thread; calling it twice is rejected.

{ "objective": "ship auth-rewrite", "token_budget": 200000 }

get_goal

Returns the current goal, status, tokens used, time used, remaining budget. Used by the model to self-check before deciding whether to keep going.

update_goal

Only accepts status: "complete". The model cannot pause itself, cannot un-budget itself, cannot reset the timer. Pause / resume / budget changes are user-only.

/goal (you)

/goal <objective>, /goal pause, /goal resume, /goal clear. /goal alone shows the summary.

The continuation prompt — where the magic actually lives

This is the hidden developer message Codex injects every time it auto-starts a new turn. It's not the model deciding to keep going on vibes — it's a structured re-brief.

templates/goals/continuation.md (abridged)
Continue working toward the active thread goal. <untrusted_objective> {{ objective }} </untrusted_objective> Budget: - Time spent: {{ time_used_seconds }}s - Tokens used: {{ tokens_used }} / {{ token_budget }} - Tokens remaining: {{ remaining_tokens }} Before deciding the goal is achieved, perform a completion audit: - Restate the objective as concrete deliverables. - Build a prompt-to-artifact checklist mapping every requirement to concrete evidence (files, commands, tests, PR state). - Do not accept proxy signals (passing tests, "looks done", effort spent) as completion by themselves. - Treat uncertainty as not achieved. Keep working. Only call update_goal when the audit shows the objective is actually achieved. Do not mark complete because the budget is nearly exhausted or because you're stopping work.

Two things to notice. First, the objective is wrapped in <untrusted_objective> and XML-escaped — Codex assumes the goal text might be a prompt-injection attempt and tells the model not to treat it as instructions. Second, the prompt is aggressively anti-completion: uncertainty is not done.

What happens when the budget runs out

The goal flips to budgetLimited and Codex injects a different developer prompt:

templates/goals/budget_limit.md
The active thread goal has reached its token budget. The system has marked the goal as budget_limited, so do not start new substantive work. Wrap up this turn soon: summarize useful progress, identify remaining work or blockers, and leave the user with a clear next step. Do not call update_goal unless the goal is actually complete.

Critical detail: a budget-exhausted goal is not a complete goal. The model is explicitly forbidden from declaring victory just because it ran out of tokens.

Token accounting — what actually counts

Per goal_token_delta_for_usage():

delta = non_cached_input + max(output_tokens, 0)
  • Cached input is free. If your prompt cache hits, the goal isn't charged.
  • Reasoning tokens aren't double-counted. They're already inside output_tokens.
  • Wall-clock time is tracked separately, in seconds, alongside tokens.
  • The update_goal call itself doesn't count. Bookkeeping shouldn't burn the budget.

Interrupts, pauses, and resumes

You hit Ctrl-C

The active turn aborts. The runtime accounts the partial progress, then flips the goal to paused. No more auto-continuation until you resume.

You re-open the thread tomorrow

On thread resume, paused goals are auto-reactivated. The token and time counters carry over from the state DB — they're persisted, not in-memory.

You're in plan mode

Goals are ignored in plan mode. No accounting, no continuation. Plan mode is for thinking; goals are for doing.

The model tries to pause itself

Rejected. update_goal only accepts complete. Pause / resume / budget changes are strictly user-controlled.

You type a message mid-loop

Not blocked. Your message gets queued, and at the next turn boundary it lands instead of the auto-continuation prompt. The runtime explicitly checks for queued input before deciding to auto-continue (goals.rs:1210). Steer the loop without stopping it.

How /goal compares to Ralph

Ralph is the other well-known answer to "make the LLM keep working." It's a 75-line bash script that spawns claude over and over with a fixed prompt, fresh context every time, with state persisted in three files on disk. Same problem, opposite bet.

Ralph

An external while-loop

Bash spawns claude over and over with a fixed prompt. Each call is a fresh, clean context. Memory survives between iterations through three artifacts on disk: a JSON task list (prd.json), an append-only learnings log (progress.txt), and the git history. Stops when the model emits <promise>COMPLETE</promise> or the iteration cap is hit.

Pattern, not a feature. Works with any CLI agent that takes a prompt and writes files.

/goal

An internal state machine

A first-class feature inside Codex. You set one objective with an optional token budget. The runtime owns a status machine, accounts every tool call against the budget, and auto-spawns continuation turns inside the same thread when idle. The model can only declare done after a structured completion audit.

Built into codex-rs/core. Persisted in a per-thread state DB.

Where they overlap

  • Both reject vibes-based completion. Ralph requires green typecheck + tests before committing a story. /goal requires a prompt-to-artifact checklist with real evidence before update_goal.
  • Both make stop-conditions explicit. Neither one trusts the model to "feel done."
  • Both assume the agent will hallucinate progress without external pressure. Ralph's pressure is the test suite. /goal's pressure is the audit instruction + budget meter.

Where they actually disagree

Ralph's bet: context contamination is the enemy. Long-running threads get worse — the model gets confused by old turns, repeats earlier mistakes, drifts. Ralph kills the context after every story. Memory is intentionally narrow.

Each PRD item should be small enough to complete in one context window. If a task is too big, the LLM runs out of context before finishing and produces poor code. — README.md

/goal's bet: continuity is the feature. The model has just been working on the problem; throwing away its context to start fresh is wasteful. Use a structured continuation prompt and a token budget to fight drift instead.

The honest summary. Ralph is a discipline pattern: it works because you wrote a good PRD, the test suite is real, and stories are small. /goal is an infrastructure pattern: it works because the runtime owns the state machine and the budget, so the model can't cheat the loop. Ralph is more portable; /goal is more integrated. Ralph wins when you can pre-decompose. /goal wins when the work is genuinely exploratory.

The interesting hybrid

The two patterns don't have to be either/or. You can run Ralph as the outer loop — fresh context, small stories, gated commits — and set a /goal inside each iteration to keep that single story focused. Ralph keeps the macro discipline (decomposed, CI-gated, auditable). /goal keeps the micro discipline (token-bounded, audit-gated, drift-resistant within the iteration). The bash script handles "what to do next." The state machine handles "are we done with what we're doing right now."

That's probably where this is heading: external orchestration patterns calling into agents that have their own internal loop primitives. Ralph showed the pattern; /goal is the runtime catching up.

The gotcha — /goal makes prompting expensive again

GPT-5.5 is so good at inferring intent from existing context that we all got lazy with prompting. On a normal thread you can throw a half-formed sentence at it and it figures out what you meant — the surrounding turns do the prompting work for you. /goal exposes this. On a fresh project, a vague /goal produces mush, because the model has no prior turns to absorb your intent from, and now it's about to spend thirty turns of autonomous work compounding whatever it guessed.

Fuzzy intent at turn one compounds across thirty turns of unsupervised work. In normal mode, a bad prompt produces one bad turn and you correct it. In /goal mode, a bad prompt produces a runaway.

The fix isn't to write a longer objective string. It's to do a setup interview before flipping the autonomy on — agree on outcome, done criteria, decision style, and ask-before boundaries. Other people are already building this; the @qhn/pi-goal skill on Pi explicitly doesn't start autonomous work immediately — /goal <intent> first opens a setup interview where the assistant and user agree on those four things before the loop starts. Codex's /goal doesn't do this yet, but you can do it manually: treat the first few turns as the interview, only flip to /goal once you've actually agreed on what done means.

This pairs directly with the completion audit. The audit only works if you defined the done criteria. If you didn't, the model audits against its own guess of what you wanted — that's not verification, that's the model marking its own homework.

Why this matters

Most agent loops are per-turn. You ask, it answers, you ask again. /goal is the first first-class multi-turn primitive in Codex: a persistent objective with its own budget, its own status machine, its own completion audit, and its own self-driven continuation. The hard part isn't auto-continuing — anyone can put a while loop around an LLM. The hard part is the discipline: the runtime owns state transitions, the model can only declare done after an evidence-based audit, the budget is real, and a budget hit doesn't get to masquerade as completion.

It's a small feature with a lot of opinions baked into it.
