1. Escalating Fallback Pipelines

Source: "Stop Getting Blocked: My Escalating Web Scraper Skill" (Daniel Miessler)
Concept

Daniel built a web scraper skill that tries 4 methods in sequence, only escalating when the previous one fails:

  • Tier 1: Anthropic's native web fetch tool (fastest, free, no dependencies)
  • Tier 2: curl with real browser headers (bypasses basic bot detection)
  • Tier 3: Playwright/Chromium with full JS execution (handles SPAs, gets full DOM)
  • Tier 4: Bright Data MCP with 150M residential proxy IPs (for Cloudflare-blocked sites, ~$0.31/day)

The general pattern is try-cheap-first with automatic escalation on failure. This generalizes beyond web scraping:

  • Model selection: try Haiku → Sonnet → Opus, escalating only when the cheaper model fails
  • Code generation: try direct edit → try with more context → spawn a subagent
  • API calls: try cached response → try primary API → try fallback API
  • Research: try local grep → try MCP search → try web search

The skill self-documents all four tiers in its SKILL.md. The escalation logic lives in the skill's instructions — Claude reads the tiers and tries them in order.

Why This Matters for the Course
Ray's course covers skills extensively but has no dedicated video on multi-tier fallback patterns. This is a generalizable architectural primitive — the "try cheap first, escalate on failure" pattern applies to model selection, code generation strategies, API calls, and research workflows.

2. Skill-to-Skill Composition (Chaining Skills)

Source: "My Art Skill With Nano Banana 3" (Daniel Miessler)
Concept

Daniel's art skill chains multiple skills together in a synchronous pipeline:

  1. Story Explanation Skill — takes any content (blog post, book, idea) and breaks it into 24 conceptual sections in simple language (ELI5 / Paul Graham / Feynman style)
  2. Be-Creative Skill — adds entropy/randomness to prevent repetitive outputs
  3. Art Prompt Composition — reads the aesthetic identity file + the 24 sections and creates a visual composition
  4. Nano Banana 3 (Flux) API call — renders the image via CLI

This is different from subagents. Subagents are spawned as independent workers. Skill chaining is synchronous — one skill explicitly calls another, passing structured output between them. It's like function composition: art(creative(explain(content))).

The art skill also has a routing system: 14 different workflows (artistic image, workflow diagram, mermaid diagram, comic strip, Twitter header, etc.) dispatched from a routing table in the system prompt. Each workflow lives in a workflows/ subdirectory inside the skill folder.

Why This Matters for the Course
Ray covers skills and subagents separately but not skills calling other skills as composable building blocks. This is function composition applied to agentic workflows — a powerful abstraction for building complex multi-step creative and analytical pipelines.

3. Triage Before Fix (Pre-filter Agent)

Sources: Arshan Dabirsiaghi at Pixee, Harry Wetherald at Maze
Concept

Two independent sources converge on the same insight:

Pixee's lesson: They built the world's best vulnerability fixing tool, but it kept "fixing" things that weren't actually vulnerable. They learned the hard way that to build a great fixer, you must first build a great triager. If you ask an agent to "fix a vulnerability," it will do so even when there isn't one — agents are eager to please.

Maze's card analogy: Most prioritization tools try to sort 52 cards by importance. Maze's insight: 48 of those cards shouldn't be in the deck at all. The first agent doesn't prioritize — it REMOVES cards.

The general principle: every agent pipeline should have a triage/filter step BEFORE the action step. The triage agent's job is to answer: "Should we even be doing this?" If no → stop. If yes → proceed to the action agent.

Pixee's specific technique for triage: rather than asking an LLM to reason about whether a vulnerability is real (unreliable), they strip the code down to just the suspicious portion and fuzz it deterministically. Low token cost, strong evidence. Pattern: use LLMs for reasoning but reach for deterministic tools (fuzz, compile, run) to CONFIRM conclusions.

Diagram
flowchart LR IN["52 Items\nEnter Pipeline"] --> TRIAGE["Triage Gate\n'Should we act?'"] TRIAGE -->|"48 items: NO"| DROP["Discarded\n(no action)"] TRIAGE -->|"4 items: YES"| ACTION["Action Agent\n'Fix the issue'"] ACTION --> OUT["4 Fixes\nShipped"] style IN fill:#24283b,stroke:#bb9af7,color:#c0caf5 style TRIAGE fill:#24283b,stroke:#e0af68,color:#e0af68 style DROP fill:#24283b,stroke:#565f89,color:#565f89 style ACTION fill:#24283b,stroke:#7aa2f7,color:#c0caf5 style OUT fill:#24283b,stroke:#9ece6a,color:#9ece6a
Why This Matters for the Course
Most agentic coding tutorials show agents that immediately act. This pattern adds a critical verification step that prevents wasted work and broken trust. The "eager to please" failure mode is something every Claude Code user encounters.

4. Sequential Agent Specialization with Early Exit

Source: Harry Wetherald at Maze
Concept

Instead of one smart agent trying to figure out everything, build separate agents for each question, chained sequentially with early exit:

  • Agent 1: "Can this be exploited?" → If NO → STOP
  • Agent 2: "How bad is it?" → If LOW → STOP
  • Agent 3: "Who owns this code?" → Route to owner
  • Agent 4: "What's the fix?" → Generate fix
  • Agent 5: "Create the PR" → Ship it

Each agent can terminate the chain if its answer makes the rest unnecessary. This is dramatically more efficient than a single agent reasoning about everything — most items exit early.

This maps directly to coding workflows:

  • Agent 1: "Is this bug real or a false positive?" → If false positive → STOP
  • Agent 2: "Is it in code we own?" → If third-party → file upstream issue → STOP
  • Agent 3: "What's the minimal fix?" → Generate fix
  • Agent 4: "Do tests pass?" → If yes → create PR

Key insight from DARPA (via Matthew Brown): the most important first question is "should you even be using AI for this?" Use deterministic code wherever possible; use AI only where judgment is actually required.

Why This Matters for the Course
More specific than Ray's existing coordinator-worker pattern. The early-exit design saves significant compute and prevents the "yes bias" where agents always find a reason to act. Most items exit at Agent 1 or 2.

5. Agent-to-Agent Communication Across Time

Source: Neatsun Ziv at OX Security
Concept

When OX Security's agent adds security-critical code (e.g., input sanitization), it adds a comment: // SECURITY: This sanitization prevents XSS. Do not remove.

Without this comment, a future agent session will see the code as unnecessary/dead and remove it for "clean code" reasons. The agent has no memory of WHY the code was added — it just sees what looks like redundant logic.

This is agent-to-agent communication across time via inline code comments. The pattern:

  • Agent A adds code + leaves a breadcrumb explaining WHY
  • Agent B (days/weeks later) reads the breadcrumb and preserves the code
  • Without the breadcrumb, Agent B undoes Agent A's work

This extends beyond security:

  • Performance: // PERF: This caching prevents N+1 queries on the dashboard page
  • Compatibility: // COMPAT: Safari requires this prefix until 2027
  • Business logic: // BIZ: Legal requires this disclaimer per GDPR Art. 13

The broader principle: when an agent makes a decision, it should leave a trace of its reasoning, not just its output. Future agents (and humans) need to understand WHY, not just WHAT.

Why This Matters for the Course
This is a concrete, immediately actionable pattern. Every Claude Code user has probably had an agent undo something a previous session added. Teaching agents to leave breadcrumb comments is a simple habit with outsized impact.

6. Just-in-Time Context Injection

Source: Neatsun Ziv at OX Security
Concept

Instead of loading all context upfront (RAG-dumping), inject context only when the agent is about to take a specific action:

  • About to write an API call? → Inject the security constraints for THAT specific API
  • About to import a dependency? → Inject the CVE data for THAT specific package
  • About to modify a database query? → Inject the performance guidelines for THAT table

This is different from progressive disclosure (which Ray covers in Context Engineering). Progressive disclosure is about structuring context in layers. Just-in-time injection is about timing — the context arrives at the exact moment it's relevant, triggered by the agent's own actions.

Implementation via hooks or MCP: a hook watches for specific agent actions (e.g., "about to install a package") and injects relevant context before the action executes. Or an MCP server that the agent calls automatically based on skill instructions.

OX Security's specific implementation: they connect to the org's CI/CD pipeline, artifact storage, cloud deployment, runtime, and APIs via a graph. When the agent touches code related to any node in that graph, the relevant constraints flow in automatically.

Why This Matters for the Course
This is a more sophisticated version of context engineering that goes beyond file-level progressive disclosure into action-level context triggering. It's the difference between "here's everything you might need" and "here's exactly what you need right now."

7. Workflow Routing Tables Inside Skills

Source: "My Art Skill With Nano Banana 3" (Daniel Miessler)
Concept

Daniel's art skill has one entry point but 14 different behaviors: artistic image, workflow diagram, mermaid diagram, comic strip, Twitter header, blog header, infographic, etc.

The routing lives in the skill's system prompt as a table mapping keywords/intent to workflow files. Each workflow is a separate markdown file in a workflows/ subdirectory:

skills/art/
├── SKILL.md (routing table)
├── aesthetic.md (brand identity)
└── workflows/
    ├── artistic-image.md
    ├── workflow-diagram.md
    ├── comic-strip.md
    ├── twitter-header.md
    └── ... (14 total)

This keeps the main skill context lean — only the routing table is loaded initially. The specific workflow instructions are loaded only when dispatched.

8. Aesthetic/Brand Identity Files

Source: "My Art Skill With Nano Banana 3" (Daniel Miessler)
Concept

A standalone markdown file that encodes visual brand identity:

  • Color palette (e.g., "Tokyo Night + Tron + Anthropic purple")
  • Style descriptors (line weight, cartoon level, detail density)
  • Typography preferences
  • Signature/watermark placement ("Kai" signature, bottom-right corner)
  • Mood/tone (dark, futuristic, clean)

This file is read by any creative skill at runtime. It acts as a persistent context asset — change it once, and all creative output across all skills updates automatically.

This is the "company as a file system" idea applied specifically to personal brand/creative identity. A reusable context file that multiple skills share.

9. Entropy Injection

Source: "My Art Skill With Nano Banana 3" (Daniel Miessler)
Concept

A "be-creative" skill that deliberately adds randomness/variation before creative generation. Based on Andrej Karpathy's observation that both humans and LLMs "collapse" over time — they converge on the same patterns, phrases, and visual styles.

The skill runs BEFORE the main creative task and introduces variation:

  • Random style modifiers
  • Unexpected combinations
  • Deliberate constraints that force novel solutions

This is entropy injection as a named, repeatable technique. Without it, the 10th image you generate looks very similar to the 1st.

10. Observability-First Agent Rollout

Source: Jiquan Ngiam at MidMCP
Concept

The enterprise pattern for safely rolling out AI agents:

  1. MONITOR: Turn on logging. Watch what agents actually do for a few days.
  2. LEARN: Discover patterns — secrets being pasted into prompts, unauthorized MCP servers being installed, risky bash commands.
  3. SUGGEST: The system auto-suggests guardrails based on observed behavior.
  4. APPROVE: A human reviews and approves the suggested rules.
  5. ENFORCE: Rules go live.
  6. REPEAT: Continue monitoring, refine rules.

MidMCP's specific implementation: they run a model over all bash commands executed in the last day, flag the risky ones sorted by priority, and suggest rules with one-click-to-add.

Don't start locked down (nobody will use it). Don't start wide open (you'll regret it). Start with observation.

Enforce\nRules go live"] ENF --> MON style MON fill:#24283b,stroke:#7aa2f7,color:#7aa2f7 style LEARN fill:#24283b,stroke:#e0af68,color:#e0af68 style SUG fill:#24283b,stroke:#bb9af7,color:#bb9af7 style APP fill:#24283b,stroke:#9ece6a,color:#9ece6a style ENF fill:#24283b,stroke:#f7768e,color:#f7768e

A pragmatic middle ground between "lock everything down" and "let agents do anything." Especially relevant for teams adopting Claude Code — start by watching, then tighten based on real data.

11. Small PR Campaigns for Backlog Burn-Down

Sources: Arshan Dabirsiaghi at Pixee, Neatsun Ziv at OX Security
Concept

Pixee COULD issue a PR fixing 500 vulnerabilities at once. But it would never get merged — no human can review a 500-change PR.

Instead, they designed "campaigns": one small, focused PR per week. Each PR:

  • Changes one thing
  • Has a clear, readable diff
  • Includes a human-readable explanation of WHY
  • Builds trust incrementally

Week 1: "Upgrade lodash to fix prototype pollution" → merged
Week 2: "Add input sanitization to /api/users endpoint" → merged
Week 3: "Replace eval() with JSON.parse() in config loader" → merged
...
Week 20: The backlog is gone. Trust is established. The team now auto-merges Pixee PRs.

OX Security describes the same pattern: define a campaign with a goal (e.g., "eliminate all hardcoded secrets by end of month"), decompose into per-developer weekly tasks distributed to each developer's IDE.

12. The 84%/16% Split

Source: Kun Chen at Atlassian
Concept

Professional developers spend only 16% of their time writing code. The other 84% is:

  • Finding information (docs, Slack threads, wiki pages)
  • Waiting for code review
  • Writing documentation
  • Dealing with incidents
  • Onboarding to unfamiliar codebases
  • Context switching between projects

Most AI coding tools optimize the 16%. The bigger opportunity is the 84%.

This reframes what "agentic coding" means — it's not just "AI writes code for me." It's "AI handles the entire software development lifecycle": finding context, planning, coding, reviewing, documenting, deploying, monitoring.

Why This Matters for the Course
Reframes the entire value proposition of agentic coding. It's not about generating code faster — it's about automating the 84% of developer time that isn't coding at all.

13. Agent Self-Reflection / "Sleeping"

Source: Kun Chen at Atlassian
Concept

Humans sleep and reorganize memory. Agents always work, always produce, never pause to consolidate.

The proposed pattern: at the end of each day (or after N sessions), the agent:

  1. Reviews all past sessions from that day
  2. Identifies what went wrong (failed attempts, wrong approaches)
  3. Extracts lessons learned
  4. Writes them into its own memory/learnings file
  5. The next day, it starts with those lessons pre-loaded

This is more than a static learnings file. The agent INITIATES its own retrospective — it's not just passively accumulating notes from human feedback.

Implementation: a cron job or scheduled task that runs Claude Code in headless mode at end of day, with a prompt like "Review today's sessions in ~/.claude/sessions/. What patterns of failure do you see? What would you do differently? Write lessons to memory.md."

14. Deterministic-First, LLM-Only-Where-Judgment-Required

Sources: Harry Wetherald at Maze, DARPA AIxCC
Concept

From DARPA's Matthew Brown: "The most important first question is: should you even be using AI for this?"

  • "Is this string longer than 100 characters?" → Don't use AI. Use len(s) > 100.
  • "Does this code pattern look like it could be exploitable?" → Use AI. Judgment required.

The anti-pattern: using AI for everything because it's available. The failure mode: ask a model "does this look vulnerable?" and it will ALWAYS try to find a reason to say yes. Too much creativity is a failure mode.

The pipeline design principle: deterministic guard clauses BEFORE LLM calls.

if file_size > 10MB: skip                              (deterministic)
if file_extension not in ['.py', '.js', '.ts']: skip    (deterministic)
if no_imports_detected: skip                            (deterministic)
→ NOW ask the LLM: "analyze this code for vulnerabilities"  (judgment)

Fights the temptation to use AI for everything. Deterministic guard clauses before LLM calls save cost, improve reliability, and prevent the "yes bias" where models always find something to flag.

15. Inductive vs. Deductive Agent Context

Source: Arshan Dabirsiaghi at Pixee
Concept

Two types of context you give agents:

  • INDUCTIVE: You explicitly tell the agent things (CLAUDE.md, skill files, system prompts). The agent receives pre-loaded knowledge.
  • DEDUCTIVE: The agent goes and FINDS things dynamically (searching codebase, reading docs, calling MCPs). The agent discovers knowledge at runtime.

The problem: too many tools is inductive overload. Notion's MCP server has 22 tools. If you give an agent 130 tools across multiple MCPs, the tool descriptions alone consume massive context, and the agent gets confused about which tool to use.

The principle: a focused agent with fewer, better tools outperforms a general-purpose agent with many tools. Design agent systems with role-specific tool sets, not everything-available-to-everyone.

MidMCP's implementation: "Virtual MCPs" — composite tool groups scoped to a specific agent role. A researcher agent gets read-only access to 5 specific tools. A deploy agent gets write access to 3 infrastructure tools. Each agent only sees its relevant tools.

Provides a useful mental model for thinking about context loading. The inductive/deductive framing helps students decide what to put in CLAUDE.md vs. what to let the agent discover, and warns against the MCP tool overload trap.

16. MCP Gateway / Proxy Pattern

Source: Jiquan Ngiam at MidMCP
Concept

Instead of every developer configuring MCP servers locally (insecure, inconsistent), run all MCP servers inside a centralized gateway:

Developer's machine → authenticated HTTP → MCP Gateway (K8s) → individual MCP servers

The gateway handles:

  • Authentication — who is this agent?
  • Authorization — what tools can this agent access?
  • Rate limiting
  • Audit logging
  • Tool-level policy enforcement
  • Consistent configuration across the team

This is the classic "proxy firewall" pattern applied to MCP. Break the direct connection, inspect in the middle, re-establish.
