THE TRAP
Building Properly First
When the requirements are uncertain, "doing it right the first time" produces expensive junk. You're guessing what the product is while also investing in making the guess robust.

week 1 * feat: add proper migration system * chore: set up feature flags * test: add coverage for edge cases week 2 * refactor: extract shared abstractions * feat: plumbing for config options week 3 — show to users ⚠ "we wanted it to work completely differently" # now you have 3 weeks of dead code # wrapped in abstractions designed for # the wrong problem

THE PATTERN
Scrappy → Spec → Rebuild
STEP 01
Build scrappy
Ugly. Hard-coded. No tests. Just get the feel of the thing in hand as fast as possible.
→
STEP 02
Feel it
Put it in front of users. Find the foot-guns. Discover what the real requirements are.
→
STEP 03
Write the spec
Now you know the shape of the problem. The spec writes itself — informed, not guessed.
→
STEP 04
Rebuild
Throw the prototype away. Rebuild the proper version from the spec. Migrate data if needed.
Key insight: The prototype is not the product. It's a research artifact — its job is to produce the spec, not to become the codebase.

Half the time, v1 is the ship

WHY NOW
AI rewrites > refactors
AI models write new code faster and cleaner than they refactor crusty code. That flips the old "throwing away the prototype is wasteful" math. Now the rebuild is the cheap part.

REFACTOR EXISTING ⚠ inherited assumptions ⚠ conflicting patterns ⚠ dead code branches ⚠ partial migrations   the model has to both understand AND change
REBUILD FROM SPEC ✓ clean slate ✓ one consistent pattern ✓ no dead paths ✓ spec as north star   the model only has to generate — not decode

WHY IT WINS
Less surface, more steering
The bigger the solution, the more bugs it has AND the harder it is to turn when you realise you're going the wrong way. Scrappy protects your ability to change direction.
theo · on Vercel's rename button
"When you do the scrappy thing, it's less surface area that can go wrong. The bigger the solution is, the more likely you are to have bugs, and the harder it is to steer in a different direction if it turns out you're going the wrong way." — Theo, on why Vercel shipped a browser-native rename input # scrappy isn't about being lazy # it's about keeping the turning radius tight # until you know which direction to point

WHEN TO USE
Use it when the problem is fuzzy
USE IT
New domain
You don't know what the customer actually wants. You're guessing. The prototype replaces the guess with evidence.
USE IT
New product shape
The feel matters and can't be speced on paper. You need to hold the thing before you can describe it.
CAREFUL
Sensitive data
If there's real user data involved, plan migrations up front. The rebuild is free — the data move isn't.
SKIP IT
Well-trodden work
CRUD, standard integrations, things you've built ten times. Just write the real version — the spec is already in your head.
Rule of thumb: the more uncertain the requirements, the more the prototype pays for itself. The more certain they are, the more the prototype is just extra work.

TL;DR
The Theo Method
Build scrappy. Learn the shape. Write the real spec. Rebuild from scratch. The prototype's job is to make the spec honest — not to become the product.
Old math: "throwing code away is wasteful." New math, with AI in the loop: refusing to throw code away is wasteful.
