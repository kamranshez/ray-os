LEVEL 1

The Concept

What the Monitor tool is, in 60 seconds

Claude Code has a tool called Monitor that runs a shell script in the background and sends you a notification every time the script prints a line. It's like setting up a live alert system — you keep working, and events come to you.

Three Ways to Run Commands

Claude Code can run shell commands in three modes. Monitor fills the gap between the other two.

◼

Bash (Foreground)

Blocks Claude completely. Can't do anything else until the command finishes.

BLOCKING
▶

Bash (Background)

Fire-and-forget. Gets ONE notification when the process exits. No updates during.

FIRE & FORGET
⚙

Monitor

Live event stream. Each stdout line becomes a notification. Claude keeps working.

STREAMING

Think of it like ordering food. Foreground Bash is standing at the counter waiting. Background Bash is ordering delivery — you only hear a knock when it arrives. Monitor is like a live kitchen cam — you see each dish being prepared and can react the moment something goes wrong.

When to Use Each

Scenario Tool Why
Quick command (<30s) Bash Just wait for it
Long build you don't need updates on Bash + run_in_background Fire and forget, get notified when done
Deploy status, CI pipeline, log tailing Monitor You want to see each status change as it happens
Session-long PR comment watcher Monitor + persistent: true Runs until you stop it or the session ends
LEVEL 2

Using It

API parameters, copy-paste recipes, and mistakes to avoid

API

The Four Parameters

Every Monitor call takes exactly four fields. All required.

Monitor({ description: "Vercel deploy status", // Shown in every notification command: "while true; do ...", // Shell script. Each stdout line = one event timeout_ms: 300000, // Kill after 5 min (max: 3600000) persistent: false // true = no timeout, runs until TaskStop })
Parameter Type Notes
description string Appears in every notification's <summary>. Be specific.
command string Shell command. Only stdout triggers events. Stderr goes to output file.
timeout_ms number Default 300000 (5 min), max 3600000 (1 hr). Ignored when persistent.
persistent boolean Session-length watches. Stop with TaskStop({task_id: "..."})

Only stdout matters. Stderr is written to the output file silently — it does not trigger notifications. Redirect noise with 2>/dev/null and keep stdout clean and selective.

RECIPES

Copy-Paste Recipes

Tested in production. Each was debugged through real use.

Vercel Deployment

Polls every 15s, reports Building/Ready/Error, exits on completion.

sleep 15 # wait for deploy to register URL=$(vercel ls myproject --scope myteam 2>/dev/null | head -1) echo "Tracking: $URL" while true; do RAW=$(vercel inspect "$URL" --scope myteam 2>&1 | grep -a "status") STATUS=$(echo "$RAW" | sed 's/.*status/status/') echo "$(date +%H:%M:%S) $STATUS" if echo "$RAW" | grep -aq "Ready"; then echo "DONE"; break; fi if echo "$RAW" | grep -aq "Error"; then echo "FAILED"; break; fi sleep 15 done

GitHub Actions Workflow

Watches a workflow run until it completes or fails.

while true; do STATUS=$(gh run list --workflow=release.yml --limit=1 \ --json status,conclusion \ -q '.[0] | "\(.status) \(.conclusion)"' 2>/dev/null || true) echo "$(date +%H:%M:%S) $STATUS" if [ "$STATUS" != "in_progress " ] && [ "$STATUS" != "queued " ]; then echo "DONE: $STATUS"; break fi sleep 30 done

Log Tail (Persistent)

Runs for the whole session. Only errors come through. Use persistent: true.

tail -f /var/log/app.log | grep --line-buffered "ERROR\|FATAL\|PANIC"

File Watcher

React to file changes in a build directory.

fswatch -r ./dist 2>/dev/null | while read f; do echo "Changed: $(basename $f)" done
PITFALLS

Things That Will Bite You

Every one of these caused a real monitor to silently produce no events or incorrect output.

Pitfall What Happens Fix
No --line-buffered Pipe buffering delays events by minutes. Grep collects ~4KB before flushing. Always grep --line-buffered in pipes
Unicode in CLI output Tools like vercel use Unicode bullets. Grep matches but sed/awk choke. Use grep -a (binary-safe). Test with cat -v first.
Wrong command for status vercel ls shows URLs only, not status. Grep for "Ready" matches nothing. Use vercel inspect <url>. Always test raw output first.
No error handling One network blip kills the entire monitor. Add || true after fallible commands
Too much stdout Raw logs trigger the 30-second flood kill. Filter aggressively with grep, jq, awk
Polling too fast Rate limiting or flood kill from too-frequent output. 30s+ for remote APIs. 0.5–1s for local checks.
No break on success Monitor runs forever after condition is met, wasting tokens. Always break or exit on terminal state

Test your script in a regular terminal first. Run it, watch the output, verify your grep/sed/awk matches the actual format. The #1 cause of silent monitors is a filter that doesn't match real output. Use cat -v to reveal hidden Unicode.

Monitor notifications become user messages. From the API's perspective, a monitor event looks identical to you typing something. The <task-notification> XML tags are the only way Claude distinguishes them. That's why the system prompt says: "Events are not replies from the user."

Without this, a noisy script would flood the conversation, blow up the context window, and cost a fortune in tokens.

The token bucket is like a bouncer at a nightclub. The club holds 10 people (burst). After that, one person can enter every 2 seconds (refill). If the line keeps growing for 30 seconds straight, the bouncer shuts down the venue and tells the promoter to be more selective next time.

LEVEL 4

The Internals

Implementation details — the XML format, wake-up mechanism, conversation loop, and safety rails

04

The XML Envelope

Every notification is wrapped in XML. Two formats — live events and task completion.

Live Monitor Event

<task-notification> <task-id>brovgltib</task-id> <summary>Monitor event: "Vercel deploy"</summary> <event>Status: Ready hy-abc123</event> </task-notification>

Sent for each stdout line that passes the rate limiter.

Task Completion

<task-notification> <task-id>brovgltib</task-id> <tool-use-id>toolu_abc</tool-use-id> <output-file>~/.claude/tasks/output.txt</output-file> <status>completed</status> <summary>Monitor "Vercel deploy" ended</summary> </task-notification>

Sent when the script exits, times out, or is killed.

Claude's conversation loop is a sleeping security guard. The queue is a doorbell. A "next" priority rings normally. A "now" priority is the fire alarm — it interrupts whatever's happening immediately.

06

The Conversation Loop

The core engine that processes everything — your messages, monitor events, task completions.

do { await processNextItem(); // dequeue + handle (API call, etc.) hasMore = false; let runningTasks = getRunningTasks(); // monitors, agents, bg bash let moreInQueue = peekQueue() !== undefined; if (runningTasks || moreInQueue) { hasMore = true; if (!moreInQueue) await sleep(100); // poll every 100ms while tasks run } } while (hasMore); // Loop exits = Claude is idle // New queue items restart it

The 100ms poll is critical. When monitors are running but the queue is empty, the loop sleeps 100ms and checks again. This keeps Claude "awake" to catch events without busy-waiting. The moment a stdout line hits the queue, the next poll picks it up.

08

Full Pipeline: stdout to Response

The complete journey of a single stdout line.

1. Script emits stdout line

Your shell script writes to stdout.

2. onStdout callback fires

Shell process stdout handler receives raw bytes.

3. Debouncer batches (200ms window)

Lines within 200ms are grouped into one notification.

4. Token bucket checks

Token available? Pass. Empty? Suppress. 30s sustained? Kill.

5. Wrapped in XML

Builds <task-notification> with <summary> and <event> tags.

6. Pushed to shared queue

Same queue as your messages, priority: "next".

7. Conversation loop dequeues

100ms poll picks up the item.

8. Injected as user message

Claude literally sees it as a role: "user" message.

9. Claude responds

Sees the XML, knows it's not from you, decides whether to react or keep working.

09

Feature Gate

Monitor is gated behind a remote feature flag.

// The feature flag check function isMonitorEnabled() { return getFeatureFlag("tengu_amber_sentinel", false); } // Used in the tool definition isEnabled() { return isMonitorEnabled(); // Only shows up if flag is true }

The flag tengu_amber_sentinel is read from GrowthBook remote config. Defaults to false. The tool is also deferred — its schema isn't loaded until first invocation, keeping startup fast.
