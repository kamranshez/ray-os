What the flow shows

  • Two gates, opposite directions. The only allow/deny gate (observer-gate-{taskId}) decides whether the observer itself is allowed to run. It never judges the worker's actions.
  • The gate is live, not a one-shot. It runs at arm time and again before every digest batch is delivered. Revoke permission mid-run and the next batch is the last one the observer sees.
  • Three outcomes, not two. allow / deny / error, and they are not interchangeable:
    At arm timeBefore a digest batch
    denyObserver never arms. Telemetry agent_observer_arm / arm_permission_denied.Terminal. State flips to denied, buffer cleared, no further delivery. Telemetry gate_denied.
    errorDoes not block. The arm path only tests === "deny", so an error falls through and the observer arms anyway.Transient. The buffered batch is dropped and state stays armed, so the next turn retries the gate. Telemetry gate_error.
  • "Managed policy" is only half of it. The managedHooksOnly: true flag applies to the hooks pass: hook selection reads only policySettings, so your own user/project/local hooks cannot veto an observer — only hooks from enterprise managed settings can. The permission-rule half honours the full ten-source stack (userSettings, projectSettings, localSettings, flagSettings, policySettings, cliArg, command, session, toolsNarrowing, mcpServerPolicy), so a plain "deny": ["Task(watchdog-demo)"] in your own project settings kills the observer just as dead.
  • The gate evaluates a synthetic Agent call. Tool-use id observer-gate-{observerTaskId}, input {subagent_type, description: "Observe <name>", prompt: "[observer auto-spawn] Watch agent <name> and report via ObserverReport.", run_in_background: true}. It must come back allow — ask counts as deny, because there is nobody to prompt. (defer is not a permission behavior at all; it exists only as a hook decision, which is why it appears in the hook check and not this one.)
  • The tool is called Agent; Task is a legacy alias. Rule parsing normalizes it (Task → Agent), which is why deny: ["Task(watchdog-demo)"] still matches. Worth knowing before saying "the Task tool" out loud.
  • Bypass cannot be laundered across a resume. The arming mode is persisted with the pairing, and on resume re-arm a stored bypassPermissions is downgraded to default before the gate re-runs.
  • The digest is a genuine over-the-shoulder view. After every worker turn the observer gets the real tool calls, inputs, and results. Tool inputs, tool results, and user messages are truncated at 2000 chars with a [+N chars truncated] marker — assistant text is not truncated. The line "The expected steady state is silence" comes from the harness framing prompt (delivered as the observer's first user message, not its system prompt) and is repeated in the postamble appended to every digest.
  • One channel, one power. The observer's entire tool schema is a strictObject with one key: report: string. No decision field, no updatedInput. Its checkPermissions unconditionally returns allow, and the report is queued as a message into the worker's prompt stream tagged observer:watchdog-demo.
  • It cannot block. Nothing wires the observer's output into the worker's permission system — delivery is a queued message, not a permission decision. The observer's toolset even strips the Agent tool, so it cannot spawn subagents of its own. Course-correction is persuasion, not enforcement. The human stays root.
  • Verified live: the worker built a fixture-fitted "rate table," the observer flagged it as "a hardcode wearing a rate-table costume," the note landed in the worker's stream, and the worker reverted the file and agreed.
