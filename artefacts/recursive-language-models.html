Concept explainer

Claude Code is now a
recursive language model

Every model is on a leash, and the leash is its context window. A recursive language model slips the leash: it leaves the giant input outside the model and writes code that calls other models to read it in pieces. With dynamic workflows, Claude Code now does exactly this. Point it at a repo ten times bigger than its window and it can reason across the whole thing.

Source idea: Recursive Language Models, Alex L. Zhang with Tim Kraska and Omar Khattab (MIT CSAIL), blog Oct 2025, paper Dec 2025 (arXiv:2512.24601), code at github.com/alexzhang13/rlm.

Start with the pain

The context window is a leash

A normal model has one context window. You stuff things into it, and the model reads all of it every single time it thinks. The bigger the pile, the more it has to weigh every token against every other token.

Past a certain size the model gets worse, not better, even though everything technically fits. That degradation has a name: context rot. Search makes it worse, because exploring fills the window with dead ends before it finds what matters.

one context window
a 2M line repo crammed in
→
model
re-reads all of it, every turn
→
answer
fuzzy, then it hits the ceiling
The bottleneck is not raw intelligence. It is that one window has to hold, and re-read, everything at once.

So the real question is not how to get a bigger window. It is how to stop needing one.

The reframe

Context by reference, not by value

Here is the move. Stop passing the data by value, copied into the window. Pass it by reference, left outside as an object the model reaches into with code.

The long input is loaded as a variable in a code environment. The model is handed only a little metadata about it: how long it is, a short preview, and how to reach in. Then it writes code to peek, grep, slice, and pull back only the pieces that matter.

By reference (recursive LM)

And the substrate is swappable

One quick definition, because it comes up a lot. A REPL, short for read-eval-print loop, is just an interactive coding shell. You type one line of code, it runs right away, and your variables stick around for the next line. Python's prompt is a REPL. A Jupyter notebook cell is a REPL. The original paper uses a Python REPL, but that is the demo, not the definition.

The load-bearing choice is that the context lives outside the neural network, as an object you only touch through code. Lots of things can be that object.

A Python REPL
the prompt as a string variable you slice with code. The version in the paper.
A filesystem + bash
files are already addressed variables. Bash is already a REPL. grep, head, and a shell give you the same thing.
Any symbolic env
anything the model can query programmatically to read part of a thing it never fully loads.
The common core: the input is an object, navigated by code. Not tokens, poured into a window.
"Bash is already a REPL. Files are already addressed variables." The substrate is swappable. The principle is not.
Prior work has explored ways to address this by storing context as an object that lives outside the context window. For example, context can be an object in a REPL that the LLM programmatically accesses by writing code to filter or slice it. Anthropic engineering, "Scaling Managed Agents: Decoupling the brain from the hands" (Apr 2026). That one sentence is essentially a definition of a recursive language model.
The obvious question

If the main model never reads the input, who does?

A fair thing to ask. A different model does. Many of them, actually. The root model only ever sees metadata and summaries. The raw text is read by separate worker calls, each one looking at a single slice in its own clean window.

root model
sees only: length, a preview, the summaries
worker call 1
reads slice 1
worker call 2
reads slice 2
worker call 3
reads slice 3
...
reads slice N
flows back up
one tiny summary per worker
Each worker is a fresh, separate model call. It reads its slice, returns a short answer, and then its window (and everything raw it read) is thrown away.

So when you hear "the model never sees the whole thing as a string," it means the root model never does. The reading is delegated to a fleet of one-shot worker models, and only their distilled answers come home. That is why the root stays sharp no matter how huge the input gets. In the paper, the root is GPT-5 and the per-slice workers are the cheaper GPT-5-mini.

So far, nothing here is new. Fanning work out to fresh-window workers is what coding agents already do. The new part is not the fan-out. It is what you are allowed to put around those worker calls. That is the next beat.
The actual unlock

The breakthrough: a subagent becomes a function in your code

This is the whole thing. The leap is not that the model can spawn subagents. Tool-calling already let it do that. The leap is that a subagent is now a function you call from inside real code, so you can wrap it in loops, conditionals, filters, batching, and stop conditions, and the model writes that control flow itself. The decomposition logic and the model calls live in the same program.

With plain tool-calling, the model emits a flat list of independent calls and every result comes back. With code, the model expresses how the calls relate: the order, the dependencies, the filter, the stop condition. And only what the code chooses to keep ever returns to the root.

Old: flat tool calls
call Acall B call Ccall D
↓
root inbox: every result returns, noise and all
New: a function inside code
for f of files { ... filter(isReal) }
agent(f)
one model call
↓
keep only survivors
↓
root gets only what the code let through
Left: the model lists calls, the room fills up. Right: control flow wraps the model call, so code decides what survives.

This is also the paper's central distinction. Its weak strawman scaffold has a code action and a separate sub-model action, but it can only delegate a few tasks it verbalizes out loud. The real recursive language model invokes the model programmatically, inside arbitrarily large loops, storing results as variables. Same two ingredients. One puts the model call inside the code. That is interleaving.

What that looks like in the shipped tool

These are real shapes from Claude Code's workflow tooling. Read them as "a subagent is just agent(...), and ordinary code surrounds it."

Interleave a sequence: each file's findings get verified the moment that file's review lands, with no waiting for the slowest reviewer. Code controls the scheduling.

const out = await pipeline(
  files,
  f  => agent(`review ${f}`, { schema: FINDINGS }),         // stage 1
  rv => parallel(rv.findings.map(x => () =>            // stage 2, as soon as stage 1 lands
    agent(`try to refute: ${x.title}`, { schema: VERDICT }))))

Let code decide whether to even spawn the next wave. If nothing was found, the whole verification phase never runs. A flat list of tool calls cannot express "skip the rest."

const found = (await parallel(finders)).flatMap(r => r.findings)
if (found.length === 0) return { note: "clean, nothing to verify" }
const checked = await parallel(found.map(verify))

And here is the part you cared about most. Results land in a variable. Code filters to the survivors. Only those come home. The rest is discarded before it ever touches the root.

const confirmed = results.flat().filter(Boolean)
  .filter(f => f.verdict?.isReal)        // the gate: code keeps only what passed
return { confirmed }                      // rejected findings never reach the root
The discard is the point, and the caveat is honest. Fan out the plain way and the model receives every result, so it has to read the noise before it can ignore it. Here the noise never arrives, because code is the gate. One catch: discarding reclaims your context and attention, not your money. The discarded subagents still ran and spent their tokens. You buy a clean root window, not a free one.
The fair objection

You could fan out before. So why does this matter now?

Be honest first. The pattern is old. Letting a model write code as its actions is old. Delegating to sub-models is old. In production agent systems, the loop of "write code, externalize the context, fan out sub-calls, aggregate" was already common before this had a name. Nobody owns it. If your gut says "this is just an agent in a for loop," you are partly right.

So here is the precise line, and it is worth getting right, because smart engineers will push on it. Fanning out can be done with plain tool-calling. That is what coding agents did. But filling a fixed template with prompts for later sub-calls is not the same as writing arbitrary code where a sub-agent is a function you call. The first lets you fan out. The second lets you say exactly how, interleaved with your own logic. Almost nothing shipped with that second kind of flexibility.

And the reason it did not is the real answer to "why now." It is a model-training story, not a framework story.

The capability was sitting there, and the model could not drive it. As the RLM author put it, code plus sub-agent calls inside a REPL "was much worse than just asking the model to do sub-calls. This is mainly a model training issue." The primitive existed for a year. Models simply could not steer it reliably. Freeform code with sub-agents as functions is hard to train, hard to guardrail, hard to sandbox, so it never became a serious thing. Nothing was missing except a model good enough to write and run the code.

That is where Opus 4.8 comes in, and it is the most interesting part. This model has very likely been trained with exactly this behavior in mind, through reinforcement learning, to write and steer these orchestration programs reliably. Anthropic credits it with better tool-triggering, longer-running agents, and stronger long-context handling, which is precisely the skill set this pattern needs. The capability stopped being a research idea the moment a frontier model was trained to actually drive it.

Worth a precise footnote so you do not overclaim on camera. The exact phrasing "perhaps the first frontier model seriously trained to be a recursive language model" is the RLM author's framing, not an official Anthropic claim. But the direction is well supported: in the paper, a small model post-trained on about 1,000 recursion traces jumped roughly 28%, and the scaffold handled over 10M tokens with off-the-shelf models and no fine-tuning. The behavior is clearly trainable, and this release is the first time it shows up in a shipping frontier model.

The payoff

Now the three ways line up

Take everything you just saw and point it at a real job: a full review across a codebase that does not fit. There are three ways to run it, and they get better in order.

Option 1 · do not

Load everything into the main context

Pour the whole codebase into one window and ask it to make decisions. It will not fit, and even the part that fits rots. The model drowns. This is the problem restated, not a solution.

Option 2 · better

Fan out a bunch of subagents

Split the work across subagents, each reading part of the codebase in its own window. Much better, because no single window holds everything. But every subagent dumps its full result back into your main context, useful or not. The window fills with noise, and you have almost no control over what comes back. This is the part people call old news. They are right that it exists.

Option 3 · this is the RLM

Fan out subagents, orchestrated by code

This is everything from the last two beats, made concrete. Code drives the fan-out: it greps to narrow, decides how many batches and subagents, runs them inside loops and conditionals, then keeps only the ones that found something useful and discards the rest. Only the real insights come home. Same subagents as Option 2. The difference is that the model wrote code to gate what survives, and Opus 4.8 is finally good enough to write that code well. That is a recursive language model.

The whole argument in one line. Option 2 is fan-out. Option 3 is fan-out plus a gate the model wrote. The gate is the part that was hard, and it is the part that just started working.
Putting it together

So a Workflow is a recursive language model

Now Option 3 is just literal. A dynamic workflow in Claude Code is the recursive language model pattern made concrete, with the REPL swapped for a shell and a script.

The root model writes one JavaScript file: the orchestration program. Inside it, agent(...) is a function call to another model. The deterministic JS, the loops, the fan-out, the conditionals, is the decomposition, and it spends zero model tokens. Only the leaf agent() calls cost anything, and each one gets a brand new, empty window, does one job, and returns only a compact result. The root's own context barely grows.

// the root model wrote this script once. each agent() call is a model.
const files = listChangedFiles()              // the raw material stays out here

// fan out: one fresh-context model per file
const findings = await parallel(files.map(f => () =>
  agent(`review ${f} for bugs`, { schema: FINDINGS, model: 'haiku' })))

// the root stitches the summaries. it never read a single file.
return await agent(`synthesize: ${JSON.stringify(findings)}`)

Notice the inversion. In a normal chat, the model decides each next step and the work piles into one window. In a workflow, JavaScript decides the control flow and the model only does leaf work in throwaway windows. That is "the model writes the loop," shipped.

The payoff in practice

What is now possible, and why it was not before

Back to that review job. The headline: run a real analysis across a repo that does not fit in the window. Not retrieve one snippet. Touch everything.

Before: one window

You point Claude at a 2.3M line monorepo and say "audit every module for this unsafe auth pattern." It greps, opens files, and each file it reads is now parked in the one window forever. Around file 150 the window is bloated, it forgets findings from file 12, contradicts itself, and somewhere near 5% of the repo it hits the ceiling and stops. Honest answer: infeasible. Your fallback is 40 separate chats stapled together by hand.

After: a dynamic workflow

The orchestrator lists the files and groups them into batches (one cheap call). It fans out, roughly 10 to 16 at a time, until all of them drain. Each subagent opens only its batch in a clean window and returns one tiny verdict like {module, unsafeCallSites, severity}. Its scratch work is discarded. The root then synthesizes a few hundred one-paragraph verdicts (which do fit) into one ranked migration plan. The repo never had to fit anywhere.

And it is journaled. If it dies at batch 180, you resume and 1 to 180 replay from cache. You pay only for 181 onward.

The reason this is new is not that any single piece is new. It is that each capability below had a hard blocker before, and putting the model call inside code removes it.

Near-unbounded context

Was impossible because

every file the model read stayed in the one window. You ran out of room a few percent into a big repo.

Now works because

each slice reads in its own window and is discarded after. Total material is bounded by your token budget, not by any one window.

Selective attention

Was impossible because

a single model cannot un-read its input. Once a chunk is in the window, it costs attention forever, relevant or not.

Now works because

plain code greps and filters first, so irrelevant chunks are skipped before any model call is ever made.

Long-horizon autonomy

Was impossible because

a run that went for hundreds of steps drowned in its own accumulated context and started to drift and contradict itself.

Now works because

the loop's state lives in variables, not in the window. The root can drive hundreds of steps without rot, with a hard agent cap so cost cannot run away.

Self-verification

Was impossible because

checking the work competed for the same window as the work itself, so verification made the rot worse.

Now works because

each skeptic runs in a clean window and is told to refute one finding. Only the verdicts return, and you keep what survives a majority.

The one-liner. A Workflow turns Claude Code from "a model you talk to" into "a model that writes a program that calls models." That is a recursive language model. It is why it can read far more, think far longer, and stay sharp far longer than any single window allows.
So you do not get burned

Honest limits, stated plainly

These are the things a sharp viewer will push back on. Say them first.

It is just an agent in a for loop, nothing new.
Partly true. The loop is old. The new part is that the model writes the loop, a sub-agent is a function inside it, and the context lives outside the window as an object the code navigates. Lead with that distinction and you are honest. Oversell "brand new paradigm" and engineers will call it out.
It recurses forever, all the way down.
No, and the limits are worth knowing. A sub-agent cannot spawn its own sub-agent. And a workflow can call another workflow only one level deep: the workflow it calls cannot itself call a third one. What does nest freely is the plain control flow. Inside one script, a pipeline can sit inside a pipeline, and a parallel fan-out can sit inside a pipeline stage, as deep as you write it. So you get depth from how you structure the code, not from workflows calling workflows. For real model-level recursion past one level, a sub-agent has to shell out to a fresh Claude instance.
Live code and frozen code are the same.
The deepest difference. A pure RLM writes its control flow live and can re-slice based on what it just saw. A Workflow's control flow is JavaScript the model authored once, before any result is known. It cannot rewrite its own loop mid-run. You trade live adaptivity for resumability and reproducibility.
The closing line. Claude Code stopped being a model you talk to. It is now a model that writes a program that calls models, and decides in code what is worth keeping. That is a recursive language model, and that is why it can take on a job that never fit in the window at all.
